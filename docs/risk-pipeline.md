# 손님 상태 · 결제 · 출구 판정

지금까지는 "선반 앞에서 물건을 집었을 가능성"(TAKE 후보)까지만 알아냈다.
이 문서의 단계가 그 결과를 이어받아 **계산하지 않은 물건을 가진 채 출구로 가는 손님**을 찾는다.
입장부터 경보까지가 처음으로 끝까지 이어진다.

## 1. 흐름 — 손님 한 명으로 보면

| 시각 | 영상 속 일 | 시스템이 기록하는 것 |
|---|---|---|
| 10초 | 손님 3 이 선반 앞에서 멈춰 손을 뻗음 | TAKE 후보 1건 → 손님 3: 집기 1 |
| 30초 | 계산대 구역에 서 있을 때 POS 에 "1개 결제" 기록 | 그 순간 계산대의 손님 = 3 → 손님 3: 결제 1 |
| 45초 | 출구 구역에 0.5초 이상 들어섬 | 집기 1, 결제 1 → **CLEAR** |

같은 손님이 30초에 계산대를 들르지 않았다면 45초에 **HIGH_RISK** 가 되고,
그 순간의 장면이 `alerts/` 에 이미지로 저장되며 결과 영상에 빨간 박스가 3초간 뜬다.

```
IdentityObservation (계층 2) ─┐
TakeCandidate      (계층 3) ─┼─> 손님 장부 ──> 출구 판정 ──> RiskEvent
결제 기록 (POS / CSV)       ─┘   (customers.py)  (engine.py)   risk_events.jsonl, alerts/*.jpg
신원 합침 기록 (계층 2)     ─┘
```

이 단계는 tracker 도 detector 도 모른다. 앞 계층의 출력만 받는다.

## 2. 판정 규칙

| 집기 행동 | 결제 | 판정 | 뜻 |
|---|---|---|---|
| 0 | - | CLEAR | 아무것도 안 집음 |
| 1 이상 | 0 | **HIGH_RISK** | 집었는데 결제가 전혀 없음 |
| 1 이상 | 행동 수보다 적음 | REVIEW | 일부만 결제 — 관리자 확인 |
| 1 이상 | 행동 수 이상 | CLEAR | 결제함 |

### 왜 "미결제 개수 1 이상이면 경보"로 하지 않았나

처음에는 그렇게 만들었다. 그런데 실제 영상 기록으로 돌려보니 **TAKE 후보 수가 집은 물건 수와 다르다.**

- store-aisle 손님 1: 9.8~13.6초(오른쪽 선반)와 11.5~22.0초(가운데 진열대)가 **시간이 겹치는 후보 두 건**이었다.
  한 번 멈춰 선 자리가 두 선반에 걸친 것이다.
- 이대로면 1개 집고 1개 결제한 손님이 "미결제 1개"가 되어 **계산한 손님에게 경보가 울린다.**

그래서 두 가지를 바꿨다.
1. **시간이 겹치는 후보는 한 번의 집기 행동**으로 센다.
2. 그래도 개수는 정확하지 않으므로(한 번 멈춰 여러 번 손을 뻗거나, 구경만 한 것을 집기로 보기도 함),
   **개수 비교에 기대는 경우는 경보 대신 REVIEW** 로 돌린다. "결제가 전혀 없음"은 개수를 몰라도 판단할 수 있으므로 HIGH_RISK 로 둔다.

"2개 집고 1개만 계산"은 실제 절도 방식이지만, 지금 시스템으로는 탐지가 과하게 센 것과 구별할 수 없다.

## 3. 결제를 누구에게 연결하나

실제 POS 가 알려주는 것은 **"몇 시에, 몇 개를 결제했다"뿐**이고 누가 결제했는지는 모른다.
그래서 결제 순간 **계산대(CHECKOUT) 구역에 발이 있던 손님**에게 연결한다.

- 계산대에 여러 명이면 **가장 오래 서 있던 사람**을 결제자로 본다. 계산하는 사람은 머무르고, 뒤에 줄 선 사람은 나중에 온다.
- 결제 순간 계산대를 막 떠났더라도 3초 안이면 결제자로 본다(POS 시각과 영상 시각의 어긋남, 결제 후 한 걸음 물러남).
- 아무도 없으면 버리지 않고 `unmatched` 로 기록한다. 놓친 결제는 오경보의 원인이므로 추적할 수 있어야 한다.
- 결제마다 연결 결과가 `payments.jsonl` 에 남는다. `candidates` 가 2 이상이면 연결이 틀렸을 수 있다.

결제 기록 CSV (`src/risk/payments.py`):

```
time_sec,items,person_id
31.5,1,
58.0,2,3
```

`person_id` 를 비우면 위 방식으로 연결한다(실제 POS 와 같은 조건).
숫자를 적으면 그 손님에게 바로 연결한다 — **계산대 구역이 없는 영상으로 로직을 시험할 때만** 쓴다.

## 4. 신원이 나중에 합쳐지면

계층 2 는 쪼개졌던 신원을 몇 초 뒤 합친다(`docs/identity-registry.md` §3-D). 그 사이
"B" 로 기록된 집기 행동이 있을 수 있다. 장부는 합침 기록을 받아 B 의 기록을 A 로 옮기고,
합쳐지기 전 번호로 늦게 도착하는 TAKE 후보도 A 에게 보낸다.

## 5. 출구 판정의 세부

- 발이 출구 구역에 **0.5초 이상 연속으로** 있어야 판정한다. 스쳐 지나가기는 제외한다.
- 한 번 들어선 방문에는 **판정을 한 번만** 낸다. 경계에서 발 위치가 들락날락해도 2초 안이면 같은 방문이다.
- 출구를 확실히 떠났다가 다시 오면 **다시 판정한다**(그 사이 결제하러 갔을 수 있다).
- 판정 시점은 "나간 뒤"가 아니라 **출구에 들어선 순간**이다. 원래 계획의 "미결제 상태로 출구 **접근**"에 맞춘 것이고,
  나가기 전에 직원이 대응할 시간을 준다.

### 출구 구역은 쇼핑 공간과 떨어뜨려야 한다

시연 중 실제로 겪었다. 출구를 통로 끝 y 0~0.30 으로 잡았더니, 손님 1 이 **통로 끝에서 구경하던 31초**에
HIGH_RISK 가 났다. 구경하던 자리(y 0.30~0.39)의 가장자리가 출구 영역에 걸렸기 때문이다.
실제로 빠져나가는 영역(y 0.27 미만)으로 좁히자 **나가는 순간(41.5초)에 한 번만** 판정했다.

→ 출구 구역은 **문 바로 앞, 선반과 확실히 떨어진 곳**에 잡는다. 촬영 계획(`docs/filming-guide.md`)에도 반영했다.

## 6. 검증 — 지금 말할 수 있는 것과 없는 것

### 로직 검증 (단위 테스트 13개)

집고 그냥 나감 / 집고 결제 후 나감 / 안 집음 / 일부만 결제 / 겹치는 후보 / 계산대에 두 명 /
계산대에 아무도 없을 때 결제 / 여유 시간 / 스쳐 지나감 / 방문당 한 번 / 재방문 / 신원 합침 / 늦게 도착한 후보.

### 실제 영상으로 끝까지 돌리기 (store-aisle)

store-aisle 은 출구·계산대가 없는 영상이라, **흐름이 제대로 도는지만** 확인했다.
영상 안에서 실제로 빠져나가는 사람은 손님 1 한 명뿐이며(42초, 통로 끝), 그 자리를 출구로 가정했다.
계산대가 없으므로 결제는 `person_id` 를 적는 시험 방식으로 넣었다.

| 결제 조건 | 판정 (41.5초, 손님 1: 집기 행동 2번) |
|---|---|
| 없음 | **HIGH_RISK** — 경보 이미지 저장, 결과 영상에 빨간 박스 |
| 40초에 1개 | REVIEW |
| 40초에 2개 | CLEAR |

YOLO 부터 돌린 전체 파이프라인과, 저장된 기록으로 다시 돌린 결과(`replay_risk.py`)가 같은 판정을 냈다.

### 아직 말할 수 없는 것

- **경보가 실제로 얼마나 맞는지.** 출구·계산대·결제가 있는 영상이 없다. 직접 찍은 시나리오 영상이 필요하다(`docs/filming-guide.md`).
- **계산대 구역으로 결제를 연결하는 방식**은 실제 영상으로 한 번도 확인하지 못했다(단위 테스트만).
- **되돌려놓기(RETURN)는 아직 없다.** 집었다가 되돌려놓고 나가면 HIGH_RISK 가 난다(오경보).
- TAKE 후보 자체가 30% 가량 놓치고 25% 가량 틀린다(MERL). 놓친 TAKE 는 경보 누락으로, 틀린 TAKE 는 오경보로 이어진다.
- 매장 밖으로 나간 손님을 장부에서 지우지 않는다. 영상 한 편 단위에서는 문제없지만, 하루 종일 돌리려면 필요하다.

## 7. 사용법

```bash
# 전체 파이프라인 (구역 파일에 EXIT, 계산대가 있으면 CHECKOUT 필요)
python run_tracking.py --source data/videos/store.mp4 --zones zones_store.yaml --payments payments.csv

# 이미 돌린 결과로 결제·구역·기준만 바꿔 다시 보기 (몇 초)
python scripts/replay_risk.py --identities outputs/store/identities.jsonl \
    --video data/videos/store.mp4 --zones zones_store.yaml --payments payments.csv \
    --merges outputs/store/identity_merges.jsonl
```

출력: `risk_events.jsonl`(판정), `payments.jsonl`(결제 연결), `alerts/*.jpg`(HIGH_RISK 장면), 결과 영상의 빨간 박스.
