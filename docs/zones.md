# 구역(Zone) 인프라

> 원본 문서에서 구역이 필요한 곳은 두 군데다.
> **SHELF** — 사람과 선반의 근접 관계로 TAKE/RETURN 추론 (§7)
> **EXIT** — 출구 접근이 HIGH_RISK 의 조건 (§1)
> 두 용도가 "다각형을 정의하고 사람과의 관계를 판정한다"는 같은 메커니즘이므로 한 번에 만들었다.

---

## 1. 판정 방식이 구역 타입마다 다르다

이것이 이 인프라의 핵심 설계다.

| 타입 | 판정 | 이유 |
|---|---|---|
| **SHELF** | 사람 bbox 와의 **겹침 비율** | 사람은 선반 '안에' 서지 않는다. 포함 판정으로는 접촉을 잡을 수 없다 |
| **EXIT / CHECKOUT / ENTRANCE** | **발 위치**(bbox 아래쪽 중앙)가 안에 있는지 | 바닥 평면의 구역이므로 서 있는 지점이 기준 |

### 왜 발 위치로 선반을 판정하면 안 되는가 — 실측

`display_center`(통로 가운데 진열대) 안에서 **걷고 있는 사람의 발이 구역 안으로 들어온다.**
원근 때문에 진열대의 **이미지상 영역이 그 앞 바닥까지 덮기** 때문이다.
3차원 물체의 이미지 footprint 는 그것이 차지하는 바닥 면적과 다르다.

반대로 선반에 손을 뻗고 있는 사람은 몸이 선반에 겹치지만 발은 통로에 있다.
→ **선반은 겹침, 출구는 발 위치.**

### 겹침 비율은 사람 bbox 기준으로 나눈다

구역 넓이로 나누면 선반처럼 넓은 구역에서는 값이 항상 0 에 가까워 쓸모가 없다.
`overlap = (겹치는 넓이) / (사람 bbox 넓이)` 이므로 0~1 이고, 1 이면 사람이 완전히 구역 안이다.

## 2. 좌표는 코드가 아니라 파일에 둔다

구역 좌표는 **카메라 설치 위치에 100% 종속**이다. 매장이 바뀌면 `zones.yaml` 만 새로 쓴다.

```yaml
normalized: true            # 0~1 상대 좌표 (권장)

zones:
  - name: shelf_left
    type: SHELF
    polygon: [[0.00, 0.00], [0.21, 0.00], [0.19, 1.00], [0.00, 1.00]]
  - name: exit_far
    type: EXIT
    polygon: [[0.30, 0.00], [0.56, 0.00], [0.56, 0.11], [0.30, 0.11]]
```

**상대 좌표를 권장하는 이유**: 처리 해상도를 바꾸면(`--scale` 실험 등) 픽셀 좌표가 전부 어긋난다.
스케일 한계 측정에서 실제로 겪은 문제다. 상대 좌표는 프레임 크기를 알게 된 시점에 픽셀로 환산된다.
(`test_normalized_coordinates_scale_with_frame` 이 720x404 / 360x202 / 1920x1080 에서 강제한다)

### 좌표 정하는 법

```bash
python scripts/export_frame.py data/videos/store-aisle-detection.mp4 --frame 2000
```

격자가 입혀진 프레임이 저장되고, 라벨은 `상대좌표|픽셀` 형식이다.
결과 영상에도 구역이 반투명하게 그려지므로(`output.draw_zones`) 바로 확인할 수 있다.

## 3. 구현

| 파일 | 역할 |
|---|---|
| `src/zones/geometry.py` | ray casting(포함), Sutherland-Hodgman(자르기), shoelace(넓이). **외부 라이브러리 없음** |
| `src/zones/zone_map.py` | zones.yaml 로드, 프레임 크기에 맞춰 환산, bbox 와의 관계 판정 |
| `src/core/types.py` | `Zone`, `ZoneType`, `ZoneHit` 계약 |
| `scripts/export_frame.py` | 좌표 지정을 돕는 격자 프레임 출력 |
| `scripts/zone_report.py` | 신원별 구역 체류 집계 |

shapely 를 쓰지 않은 이유: 필요한 연산이 두 개뿐이고, 의존성을 늘리면 계층 분리 원칙이 흐려진다.

## 4. 첫 관측 — baseline 의 한계가 바로 드러났다

`zone_report.py` 로 전체 영상(65초) 신원별 구역 접촉을 집계했다.
SHELF 는 겹침 0.15 이상을 '접촉'으로 셌다.

| person | 관측 | shelf_left | shelf_right | display_center | exit_far |
|---|---|---|---|---|---|
| 1 | 950 | — | 312 (33%) | 286 (30%) | — |
| 2 | 1620 | — | 853 (53%) | 735 (45%) | — |
| 3 | 1476 | — | 924 (63%) | 438 (30%) | — |
| 4 | 1022 | 596 (58%) | — | 550 (54%) | — |
| 5 | 1093 | 696 (64%) | — | 984 (90%) | — |
| 7 | 396 | 356 (90%) | — | 331 (84%) | — |

**모든 사람이 선반에 30~90% 접촉한다.**

이건 버그가 아니라 당연한 결과다 — **통로를 걷는다는 것 자체가 선반 옆에 있다는 뜻**이다.
그래서 "선반에 가까웠다"는 신호만으로는 TAKE 를 판정할 수 없다.
그냥 지나간 사람과 상품을 집은 사람이 구분되지 않는다.

### 이것이 다음 단계에 주는 시사점

Phase 5 에서 Zone 규칙을 baseline 으로 고른 이유는 "가장 단순한 것으로 끝까지 이어보고
어디서 무너지는지 보자"였다. **무너지는 지점이 예상보다 앞쪽에서 드러났다.**

TAKE 판정에는 근접 외에 최소한 하나가 더 필요하다.

| 보강 후보 | 내용 | 비용 |
|---|---|---|
| **체류(dwell)** | 지나가는 것과 멈춰 서는 것을 구분 | 없음. 이미 있는 데이터로 가능 |
| **구역 축소** | 선반 전체가 아니라 **선반 면**만 좁게 지정 | 좌표 다시 잡기 |
| **속도** | 이동 속도가 느려지는 구간 | 없음. track 궤적으로 계산 |
| **Pose(손)** | 손이 선반 쪽으로 뻗었는지 | pose 모델 추가 (docs/phase5 에서 지표는 확인됨) |

위 세 개는 **추가 모델 없이** 지금 데이터로 가능하므로 먼저 시험할 가치가 있다.

---

## 5. 한계

- **EXIT 검증은 인위적이다.** 이 영상에 실제 출구가 없어 통로 안쪽 끝을 임의로 지정했다.
  전체 영상에서 `exit_far` 에 발이 들어온 사람은 0명이다. 실제 출구가 있는 영상이 필요하다.
- **구역은 카메라 한 대 기준이다.** 카메라가 늘면 구역도 카메라별로 관리해야 한다.
- **2D 이미지 좌표다.** 바닥 평면으로의 투영(homography)을 쓰면 더 정확하겠지만,
  카메라 보정이 필요하므로 지금 단계에서는 과하다.

---

## 6. 설정

```yaml
zones:
  enabled: true
  path: zones.yaml

output:
  draw_zones: true    # 결과 영상에 구역을 반투명하게 그린다
```

명령행: `--zones <경로>` `--no-zones`
