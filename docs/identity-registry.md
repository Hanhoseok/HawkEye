# 계층 2 · 매장 단위 신원 레지스트리

> 목표: **고객이 탐지된 순간부터 매장을 나갈 때까지** 같은 식별자를 유지한다.
> tracker 만으로는 불가능하다는 것이 앞선 실험에서 확인되었다.

---

## 0. 왜 tracker 로는 안 되는가

tracker 의 `lost_track_buffer` 는 **초 단위 짧은 공백**을 메우는 장치다.
현재 값 90 은 30fps 기준 **3초**이고, 이것을 키우는 방향은 막다른 길이다.

| 시도 | 결과 |
|---|---|
| ByteTrack buffer 30 / 90 / 150 | 전부 재식별 실패 (docs/tracker-comparison.md) |
| 버퍼를 9,000 프레임(5분)으로? | 이미 나간 사람까지 붙잡아 오병합 폭증 |

고객이 5분 머무르며 선반 뒤로 스무 번 사라지는 것은 tracker 가 감당할 문제가 아니다.

## 1. 구조

```
[계층 1] tracker              프레임 간 연결. 초 단위 공백 담당.
              | TrackObservation
[계층 2] IdentityRegistry     매장 안 사람들의 외형 템플릿 보관.
                              새 track 이 생기면 먼저 대조 -> 기존 신원에 잇거나 신규 입장.
              | IdentityObservation  (person_id + track_id)
[계층 3] 이후 로직            TAKE/RETURN, 상태 관리, POS, 위험 판정 — person_id 를 쓴다
```

핵심: **이 계층은 tracker 구현을 전혀 모른다.** `TrackObservation` 만 받으므로
ByteTrack 이든 BoT-SORT 든 그대로 동작한다. (아래 검증에서 실제로 증명됨)

### 설계 결정 세 가지

**1) 임베딩을 매 프레임 뽑지 않는다**

BoT-SORT 내부 ReID 는 매 프레임 모든 고신뢰 detection 에 대해 임베딩을 계산한다
(`botsort.py:174`). 레지스트리는 다음 두 경우에만 계산한다.

- 새 track 이 생겼을 때 (신원을 정해야 하므로)
- 살아 있는 track 의 템플릿 갱신 주기 (기본 30프레임)

**2) 한 사람당 템플릿을 여러 개 보관한다 (기본 5개)**

같은 고정 카메라 안에서도 사람 크기가 **4~10배** 변한다(docs/scale-limits.md).
템플릿이 하나면 "멀리 있을 때"와 "가까이 있을 때"를 잇지 못한다.

템플릿이 가득 차면 **크기가 가장 비슷한 것을 대체**한다.
오래된 것부터 버리면 최근 크기로만 쏠려 스케일 다양성이 사라지기 때문이다.
(`test_templates_keep_scale_diversity` 가 이 성질을 강제한다)

**3) 너무 작은 관측은 신원 판단에 쓰지 않는다**

텐서 65px 미만에서는 탐지 재현율이 43% 이하로 떨어지고 신원이 유실되기 시작한다
(docs/scale-limits.md). 이런 관측에는 `person_id = -1` 을 주어 **판단을 보류**하고,
그 사람이 가까워져 커지면 그때 배정한다.

임계값은 영상마다 자동 환산된다:
`화면 픽셀 기준 = min_tensor_height x 프레임의 긴 변 / imgsz`

### 안전장치

- **같은 프레임에 보이는 두 track 은 절대 같은 신원이 될 수 없다.**
  한 사람이 동시에 두 곳에 있을 수 없기 때문이다. 대조 시 이미 점유된 신원을 제외한다.
- **오래 안 보인 사람은 대조 대상에서 제외한다**(기본 30초).
  **체류 시간 상한이 아니다.** 보일 때마다 시계가 초기화되므로,
  계속 보이는 고객은 몇 분을 머물러도 만료되지 않는다.
  기준은 "마지막으로 보인 뒤 연속으로 안 보인 시간"이다.
  실제 운영에서는 EXIT 존 이벤트로 대체해야 한다. 지금은 시간 기반 임시 규칙이다.

  > **정정 기록**: 처음에는 `retire_after_frames: 900` 으로 구현하고 "30초"라고 적었으나,
  > `Frame.index` 는 **원본 프레임 번호**라서 59.9fps 인 store-aisle 에서는 실제로 **15초**였다.
  > 게다가 `lost_track_buffer` 는 **처리 프레임** 기준이라 한 시스템 안에 서로 다른 두 기준이 섞여 있었다.
  > `Frame.pts_ms`(재생 시각) 기반으로 바꾸고 설정 단위를 **초**로 통일했다.
  > 회귀 테스트 `test_retirement_uses_time_not_frame_count` 추가.

## 2. 검증 — 같은 구간, tracker 를 바꿔가며

기준 구간: store-aisle frame 1200~1598 (정답 = 4명, 그중 1명은 1.67초 사라졌다 재등장)

| 구성 | track | person | 판정 |
|---|---|---|---|
| ByteTrack 단독 | 5 | — | ❌ 분열 |
| BoT-SORT+ReID 단독 | 4 | — | ✅ |
| **ByteTrack + 레지스트리** | 5 | **4** | ✅ **복원** |

레지스트리가 만든 신원:

| person | 구성 track | 유사도 |
|---|---|---|
| 1 | t1(1200-1596) | — |
| 2 | t2(1200-1598) | — |
| **3** | **t3(1200-1458) + t5(1558-1598)** | **0.718** |
| 4 | t4(1558-1598) — 진짜 신규 | 합치지 않음 |

**tracker 를 전혀 고치지 않고** 위 계층만으로 분열을 복원했고,
같은 시점에 새로 들어온 사람은 올바르게 분리했다.

## 3. 전체 영상 검증 (65초 / 1,961 처리프레임)

| 구성 | track | person | 속도 |
|---|---|---|---|
| ByteTrack 단독 | 11 | — | 7.60 FPS |
| **ByteTrack + 레지스트리** | 11 | **6** | 8.92 FPS |
| BoT-SORT 단독 | 7 | — | 5.97 FPS |
| BoT-SORT + 레지스트리 | 7 | 7 | 5.36 FPS |

숫자만 보면 6 과 7 이 어긋나 보이지만, **구간을 맞춰보면 두 경로가 일치한다.**

| BoT-SORT 단독 | ByteTrack + 레지스트리 | |
|---|---|---|
| t1 540-2546 | p1 540-2546 | ✓ |
| t2 676-3920 | p2 688-3920 | ✓ |
| t4 966-3920 | p3 968-3920 | ✓ |
| t5 1558-3920 | p4 1558-3920 | ✓ |
| t6 1666-3894 | p5 1670-3894 | ✓ |
| **t7 1742-1742** | (없음) | **1프레임짜리 허위 track** |
| t8 3130-3920 | p6 3132-3920 | ✓ |

**실제 인원은 6명이고, BoT-SORT 단독의 7 은 1프레임 허위 track 을 포함한 과다 계수다.**

### 레지스트리가 이어붙인 5건 — 전부 독립 근거가 있다

| person | 이어붙인 track | 공백 | 유사도 | BoT-SORT 의 판단 |
|---|---|---|---|---|
| 1 | t1(540-1458) + t6(1558-2546) | 1.67초 | 0.701 | t1 이 540-2546 로 연속 ✓ |
| 2 | t2(688-1056) + t4(1060-3920) | 0.07초 | 0.890 | t2 가 676-3920 로 연속 ✓ |
| 3 | t3(968-2858) + t10(2862-3920) | 0.07초 | 0.762 | t4 가 966-3920 로 연속 ✓ |
| 4 | t5 + t12 + t13 | 2.5초 / 0.77초 | 0.686 | t5 가 1558-3920 로 연속 ✓ |

**병합 5건 모두 BoT-SORT 가 독립적으로 하나의 track 으로 본 구간과 정확히 일치한다.**
그럴듯해 보이는 수준이 아니라, 다른 방법으로 교차 검증된 결과다.

### 오병합은 없었다

레지스트리가 서로 다른 사람을 합친 사례는 없다.
특히 p6(3132-3920)는 뒤늦게 들어온 사람인데, 이미 나간 p1(540-2546)과 합쳐지지 않았다.
(둘 사이 공백은 약 9.7초로 퇴장 기준 안이므로 대조 대상이었음에도 합치지 않았다.)

## 3-B. 스트레스 — tracker 를 일부러 망가뜨려도 출력이 불변이다

`lost_track_buffer` 를 낮춰 ByteTrack 이 강제로 조각나게 만든 뒤,
레지스트리의 출력이 흔들리는지 확인했다.

| ByteTrack buffer | track 수 | **person 수** |
|---|---|---|
| 5 | **14** | **6** |
| 15 | 12 | **6** |
| 30 (기본) | 11 | **6** |
| — (BoT-SORT 단독, 참고) | 7 | 6 (실제 인원) |

track 이 11개든 14개든 **person 은 항상 6명**이다.

더 나아가 buffer 5(14조각)일 때의 신원 **구간까지 기준과 완전히 일치**한다.

| person | buffer 5 | buffer 30 (기준) | |
|---|---|---|---|
| 1 | 540-2546 | 540-2546 | ✓ |
| 2 | 688-3920 | 688-3920 | ✓ |
| 3 | 968-3920 | 968-3920 | ✓ |
| 4 | 1558-3920 | 1558-3920 | ✓ |
| 5 | 1670-3894 | 1670-3894 | ✓ |
| 6 | 3132-3920 | 3132-3920 | ✓ |

**레지스트리의 출력은 tracker 품질 저하에 대해 불변이다.**
이것이 계층을 분리한 실질적 이득이다 — tracker 를 무엇으로 바꾸든, 얼마나 나쁘게 설정하든,
뒤쪽 로직이 보는 person_id 는 같다.

## 3-C. 핵심 검증 — tracker 버퍼의 3.3배 되는 공백을 건너뛴다

앞의 실험들에서 레지스트리가 이어붙인 가장 긴 공백은 2.5초로,
BoT-SORT 의 버퍼(3초) 안이었다. **정작 이 계층을 만든 이유인 "버퍼보다 긴 공백"은
그 영상에 해당 사건이 없어 검증되지 못했다.**

그래서 `--blackout START:END` 옵션을 추가해 인위적으로 만들었다.
지정한 구간의 프레임을 검은 화면으로 덮으면 **모든 사람이 동시에 사라진다.**
tracker 는 track 을 버릴 수밖에 없고, 이후 같은 사람을 다시 이어붙일 수 있는지는
전적으로 레지스트리에 달린다.

조건: `--blackout 2000:2600` = 원본 600프레임 = **10초** (버퍼 3초의 3.3배)

| | track | person |
|---|---|---|
| 차단 없음 | 7 | 7 |
| **10초 전면 차단** | **11** | **7** |

**tracker 는 7 → 11 로 무너졌지만, 신원 출력은 7 그대로다.**

### 차단 전후 신원 구간 대조

| person | 차단 없음 | 10초 차단 | 유사도 | |
|---|---|---|---|---|
| 1 | 540-2546 | 540-**1998** | — | 차단 중 퇴장 (복구 대상 아님) |
| 2 | 676-3920 | 676-3920 | **0.842** | ✅ 이어붙임 |
| 3 | 966-3920 | 966-3920 | **0.762** | ✅ |
| 4 | 1558-3920 | 1558-3920 | **0.781** | ✅ |
| 5 | 1666-3894 | 1666-3894 | **0.807** | ✅ |
| 6 | 1742-1742 | 1742-1742 | — | 1프레임 허위 track (detector 문제) |
| 7 | 3130-3920 | 3130-3920 | — | 차단 후 입장 |

차단 시점에 매장에 있던 사람은 5명(p1~p5)이고, 그중 **p1 은 차단 구간 중에 실제로 퇴장**했다
(차단 없을 때도 2546 에서 끝난다). 즉 **복구 가능한 4명 전원을 복구했다.**

유사도는 0.762~0.842 로 임계값 0.65 를 여유 있게 넘었다.

**결론: 10초 공백에서 복구 가능한 신원을 100% 복구했다.
tracker 버퍼(3초)로는 원리적으로 불가능한 구간이다.**

### 남은 흠

p6 (1742-1742) 는 **1프레임짜리 허위 track** 이 그대로 하나의 신원이 된 것이다.
레지스트리 문제가 아니라 detector 의 오탐이지만, 신원 등록 전에
"최소 N 프레임 이상 유지된 track 만 등록" 같은 조건을 두면 걸러낼 수 있다. (미구현)

## 3-D. 천장 시점의 신원 분열 — 즉시 판정 + 나중에 합치기 + 가장자리 규칙

배경은 `docs/merl-evaluation.md` §4-E: 천장 시점(MERL)에서 쇼핑객 한 명이 두 신원으로
쪼개져(15개 중 4개 영상, 관측의 42~49%) TAKE 재현율이 0.62 에 묶여 있었다.

### 흐름을 예로 들면

손님 A 가 화면 아래쪽으로 나갔다가 12초 뒤 다시 들어온다.

1. **다시 들어오는 순간** — 사진 한 장으로 즉시 판정한다. 천장 시점에서는 이 판정이 자주 틀려
   A 가 새 신원 B 로 등록된다. 이때 몸이 화면 가장자리에 걸려 잘려 있으면 아예 비교하지 않고
   새 신원으로 둔다(가장자리 규칙).
2. **B 로 5초 동안** — 0.5초마다 사진을 한 장씩 모은다. 이 사이의 행동(선반에 손 뻗기)은
   B 의 것으로 정상 기록된다. 판정을 보류하지 않으므로 놓치는 행동이 없다.
3. **사진 10장이 모이면** — B 의 평균 외형을 "B 가 나타나기 전에 사라진 사람들"의 평균 외형과
   비교한다. A 와 0.875 이상이면 B 를 A 로 합친다. 이후 B 의 track 은 A 로 나가고,
   `identity_merges.jsonl` 에 `{"from": B, "into": A}` 가 남는다.
4. **뒤 계층** — 합친 기록을 받아 B 로 기록된 행동을 A 의 이력으로 옮긴다(상태 계층의 몫).

### 왜 이렇게 했나 — 측정으로 고른 과정

`scripts/identity_calibration.py`: MERL train 20명에서 손님이 새 track 으로 다시 나타난
**실제 순간 122건**을, 그 사람의 과거 기록과 비교했다. 다른 사람(다른 영상 손님) 오병합을 5% 로
묶었을 때 같은 사람을 이어주는 비율:

| 새 track 쪽 증거 | 같은 사람 이어줌 |
|---|---|
| 사진 1장 (즉시) | 57% |
| 연속 8장 (≈0.5초) | 67% |
| 1초 간격 5장 (≈5초) | 80% |
| **0.5초 간격 10장 (≈5초)** | **88%** |

- **연속 프레임은 평균해도 별 도움이 안 된다.** 자세가 거의 같아 잡음이 상쇄되지 않는다.
  간격을 두고 장수를 늘려야 한다.
- 그래서 "판정을 보류하고 모으기"는 버렸다. 5초를 보류하면 그동안의 행동을 잃는다.
  대신 즉시 판정하고, 5초 뒤 바로잡는다.

> **정정 기록**: 처음에는 "사진 8장을 평균하면 95%"라는 측정을 근거로 판정 보류 방식
> (`aggregate_frames: 8`, 기준 0.90)을 넣었다. 그런데 그 측정의 8장은 영상 전체에서
> 띄엄띄엄 뽑은 것이었고, 실제 레지스트리는 **연속 8프레임**을 모은다. 적용했더니
> 원래 잘 묶이던 영상 6개까지 2~4명으로 쪼개졌다. 실제 조건 그대로 다시 잰 것이 위 표다.

### 가장자리 규칙 — 여러 사람 영상에서 찾은 오병합

안전 점검(여러 사람이 나오는 영상 4개)에서 **이번 변경 전부터 있던 오병합**을 찾았다.

| 영상 | 이전 설정이 한 명으로 묶은 track | 실제 |
|---|---|---|
| people-detection | t1 + t2 + t7 / t4 + t8 + t10 | 금발 원피스 · 데님 재킷 · 체크 셔츠 / 검은 티 · 흰 셔츠 · 검은 원피스 — 전부 다른 사람 |
| topdown-plaza | t1 + t3 + t6 + t12 / t7 + t8 | 분홍 가방 여성 · 모자 쓴 남성 … / 줄무늬 셔츠 · 흰 셔츠 — 다른 사람 |

원인: track 이 생기는 순간은 사람이 가장자리로 막 들어오는 순간이라 **머리카락만** 보인다.
이런 사진끼리는 누구든 0.71~0.83 으로 닮아 보인다(기준 0.65).

대응: bbox 가 화면 가장자리(2%)에 닿아 있으면 즉시 비교하지 않고 새 신원으로 둔다.
진짜 같은 사람이면 몸이 다 보인 뒤 나중에 합치기가 잇는다.
**잘못 합치는 것(무고한 손님에게 경보)을 잠깐 쪼개지는 것(나중에 바로잡힘)으로 바꾼다.**

## 4. 이 검증이 말해주지 않는 것

- **10초는 검증했지만 분 단위는 아직이다.** `retire_after_seconds` 기본값이
  30초이므로 그보다 오래 연속으로 안 보이면 대조 대상에서 제외된다.
  (검증 당시에는 이 값이 실제로 15초로 동작하고 있었다. 위 정정 기록 참조.
   10초 공백 실험은 15초 안이었으므로 결과는 유효하다.)
  실제 매장 체류 시간(수 분)을 감당하려면 이 값과 EXIT 존 연동이 필요하다.
- **전면 차단은 실제 가림과 다르다.** 모두가 동시에 사라지므로 "누가 누구였는지"를
  헷갈릴 경쟁자가 줄어든다. 한 사람만 선반 뒤로 가려지고 다른 사람들은 계속 보이는
  상황이 더 어렵다.
- **속도 수치는 신뢰하기 어렵다.** ByteTrack+레지스트리(8.92)가
  ByteTrack 단독(7.60)보다 빠르게 나왔는데, 이는 원리상 불가능하므로 측정 잡음이다.
  비용을 주장하려면 통제된 재측정이 필요하다.
- **정답 인원수를 사람이 직접 세어 확정하지 않았다.** 두 경로가 6명에 일치한다는
  교차 검증일 뿐이다.
- 한 영상 · 한 장면 기준이며, 옷차림이 서로 뚜렷이 다른 조건이다.

## 5. 설정

```yaml
identity:
  enabled: true
  match_threshold: 0.65      # 즉시 판정(사진 1장) 기준
  max_templates: 5           # 한 사람당 외형 템플릿 수
  template_refresh_seconds: 0.5  # 사진 수집 주기. 나중에 합치기의 증거가 된다
  retire_after_seconds: 30.0 # '연속으로' 안 보인 시간. 체류 시간 상한이 아니다
  min_tensor_height: 65      # docs/scale-limits.md 의 하한
  stitch_enabled: true       # 위치·시간 근거 (3초 안, 체구 1배 거리 안이면 기준 완화)
  stitch_max_seconds: 3.0
  stitch_max_distance: 1.0
  stitch_threshold: 0.45
  late_merge_enabled: true   # 나중에 합치기 (§3-D)
  late_merge_samples: [10, 20, 40]
  late_merge_threshold: 0.875
  edge_margin: 0.02          # 가장자리에 걸린 잘린 사진으로는 즉시 판정하지 않는다
```

위치·시간 근거(stitching)는 MERL 에서 효과가 없었다. 쪼개짐이 대부분 화면 밖으로 나갔다
10~13초 뒤 돌아오는 경우였고, 화면 가장자리는 모든 손님의 출입구라 위치가 근거가 되지 못했다.
선반 뒤에 잠깐 가려지는 경우를 위해 짧은 창으로 남겨 두었다.

명령행: `--no-identity` `--identity-threshold` `--retire-after`(초) `--blackout`
