# 시스템 정리: 하드웨어·센서 동작, 데이터 파이프라인, Wi-Fi 연결

현재 설치 기준 문서 (2026-11-08). 설치·보정 절차의 세부 사항은 [README](../README.md)에 있다.

## 1. 전체 구성

```
 레인 1      레인 2      레인 3      레인 4           (검은 칸막이로 레인 분리)
 ┌──────┐   ┌──────┐   ┌──────┐   ┌──────┐
 │VL53L0X│   │VL53L0X│   │VL53L0X│   │VL53L0X│  ← 레일 뒤, 밀판 뒷면(흰 표적)을 향함
 │  I²C  │   │  I²C  │   │  I²C  │   │  I²C  │
 │ ESP32 │   │ ESP32 │   │ ESP32 │   │ ESP32 │  ← 레인마다 1대, 같은 펌웨어, 레인 번호만 다름
 └───┬───┘   └───┬───┘   └───┬───┘   └───┬───┘
     └──── Wi-Fi (UDP 브로드캐스트, 포트 4210) ────┐
                                                    ▼
                         휴대폰 핫스팟 (2.4GHz, 10.97.184.x)
                                                    │
                                     PC: python run.py --wifi
                          (수량 추정 · 이벤트 기록 · 레일 화면)
```

| 구성 요소 | 역할 |
|---|---|
| VL53L0X (레인당 1개) | 밀판 뒷면까지 거리 측정 |
| ESP32-WROOM-32 (레인당 1대) | 센서 제어, 측정값을 JSON 한 줄로 USB와 Wi-Fi(UDP)에 동시 전송. **수량 판단은 하지 않음** |
| 휴대폰 핫스팟 | ESP32들과 PC를 같은 네트워크로 연결 |
| PC Python | 보드별 수신 추적, 필터, 안정 판정, 수량 확정, ADD/REMOVE/RESYNC 기록, 화면 표시 |

## 2. 하드웨어와 센서 동작 방식

### 2-1. 측정 원리 (VL53L0X, ToF)
- 940nm 적외선 레이저 펄스를 쏘고, 반사되어 돌아오는 시간으로 거리를 계산한다. 1회 측정은 펄스를 수천 번 쏴서 평균 낸 값이다(측정 예산 33ms).
- 빔은 약 25° 원뿔로 퍼진다(40cm에서 지름 약 18cm). 그래서 빔 안의 다른 물체(바닥, 칸막이, 옆 레인)의 반사가 섞일 수 있다.
- 출력은 mm 단위지만 실제 흔들림은 표준편차 3~5mm 수준이다(현장 측정).
- 측정마다 상태를 함께 낸다. `OK`, `NO_TARGET`(표적 없음), `RANGE_INVALID`, `TIMEOUT`, `I2C_ERROR`, `NOT_CONNECTED`(배선 문제), `INIT_FAILED`.

### 2-2. 설치와 거리의 의미
```
[센서] ──빔──▶ ┃밀판┃(흰 표적)  캔  캔  캔 │앞(고객 쪽)
       거리 d                         └ 스프링이 밀판을 앞으로 민다
```
- 센서는 레일 뒤에서 밀판 뒷면의 흰 무광 표적을 본다. 검정·광택 면보다 반사가 강해 값이 안정적이다.
- 상품을 빼면 밀판이 앞으로 가서 **거리 증가 = 수량 감소**, 넣으면 **거리 감소 = 수량 증가**다.
- 수량은 매번 거리의 절대값으로 다시 계산한다. 이동량을 누적하지 않으므로 오차가 쌓이지 않는다.

### 2-3. 이 레일의 특이점: 밀판 앞 5cm 고정 블록
- 레일 길이 38cm, 밀판 앞에 약 5cm 고정 블록이 있어 빈 상태의 밀판이 앞 끝까지 나가지 못한다.
- 그래서 **첫 캔은 밀판을 조금만 민다**(실측: 1번 레인 약 17mm, 2번 레인 약 10mm). 두 번째 캔부터는 캔 지름(65~66mm)만큼 움직인다.
- 0개와 1개의 거리 차이가 작아서, **레인마다 실측한 수량별 거리표와 수량별 허용 오차**(0개·1개만 좁게)로 구분한다(3장).

### 2-4. 배선 (레인마다 동일)
| VL53L0X | ESP32 |
|---|---|
| VIN | 3V3 |
| GND | GND |
| SDA | GPIO21 |
| SCL | GPIO22 |

센서가 `NOT_CONNECTED`면 배선(특히 SDA·SCL 뒤바뀜, 빠진 점퍼선)을 확인한다. 옆 레인 작업 중 선이 빠지는 일이 실제로 있었다.

### 2-5. 펌웨어 (1.2.0, 모든 보드 동일)
- 측정은 **비차단 상태 머신**으로 한다. 시작 → 완료 확인(2ms 간격 폴링) → 결과 읽기 순서이고, 120ms 안에 끝나지 않으면 `TIMEOUT`이다. 레인당 초당 약 10회 측정한다.
- 통신 오류가 5회 연속 나면 센서를 다시 초기화한다(1초부터 최대 10초 간격). 배선을 고치면 자동으로 복구된다.
- **레인 번호는 보드 내부 저장소(NVS)에 저장**한다. 보드 이름은 `shelf-lane-<번호>`이고, `wifi_setup.py --lane N`으로 바꾼다.
- 오류가 나도 거리를 0으로 바꾸지 않고 `distance_mm: null`로 보낸다.

## 3. 데이터 파이프라인

```
ESP32                         전송                PC (Python)
──────────────────────────    ────────────────    ─────────────────────────────────────────────
VL53L0X 측정 (10회/초)   ─▶  JSON 한 줄       ─▶  UdpSource: 데이터그램 수신 + PC 수신 시각
  상태 판정                   USB Serial 115200      │
  JSON Lines 생성             UDP 브로드캐스트       ▼
                              x.x.x.255:4210      Monitor: device_id 별로 분리
                                                     · boot_id → 재부팅 감지
                                                     · sequence → 중복 버림 / 누락 집계
                                                     · uptime_ms 32비트 wrap 보정
                                                     · 수신 지연(백로그) 감지
                                                     · 보드 무응답 3초 → 그 보드 레인만 stale
                                                     ▼
                                                  LaneEstimator (레인마다 독립)
                                                     · 유효 측정만 중앙값 필터 (5~7개)
                                                     · 수량별 기준 거리·허용 오차로 후보 수량
                                                     · 1.2초 + 5샘플 이상 안정 시 확정
                                                     · 이전 확정 수량과 비교해 이벤트 1회
                                                     ▼
                                     콘솔 · logs/events.jsonl · logs/status.jsonl · 레일 화면(GUI)
```

### 3-1. 메시지 (ESP32 → PC)
```json
{"message_type":"MEASUREMENT","device_id":"shelf-lane-1","boot_id":"c1b4d7f0","sequence":11930,
 "uptime_ms":4182176,"lane_id":1,"distance_mm":345,"valid":true,"sensor_status":"OK"}
```
그 밖의 메시지: `HEARTBEAT`(1초마다, Wi-Fi 상태와 IP), `HELLO`, `WIFI_STATUS`, `LOG`, `CONFIG_ERROR`. `uptime_ms`는 보드 부팅 후 경과 시간이며 실제 시각이 아니다.

### 3-2. 수량 판단 규칙
1. **유효 측정만** 필터에 넣는다. 무효값, 600ms 넘는 공백, 지연되어 몰려온 데이터는 안정 구간을 다시 시작하게 한다.
2. 필터값 `m`과 수량 n의 기준 거리 `ref(n)`의 차이가 `허용오차(n)` 안이면 n이 후보가 된다. 이미 확정된 수량은 `허용오차 + 히스테리시스`까지 유지된다. 이 때문에 경계에서 흔들려도 수량이 왔다 갔다 하지 않는다.
3. 같은 후보가 **장치 측정 시각 기준 1.2초 이상, 5샘플 이상** 유지되고 흔들림 폭이 10mm 이하일 때만 확정한다. 스프링 반동이나 손으로 잠깐 가린 경우는 확정되지 않는다.
4. 이벤트 종류
   - 확정 수량이 바뀌면 `ADD`나 `REMOVE`를 한 번만 기록한다.
   - 프로그램을 시작했을 때는 `INIT`이다.
   - 센서 오류, 보드 끊김, 재부팅, 재입고 모드 뒤에는 관찰하지 못한 구간이 있으므로 `RESYNC`로 기록한다(입출고로 단정하지 않음).
5. 범위를 벗어난 거리는 0개나 최대 개수로 잘라 넣지 않고 `OUT_OF_RANGE`로 알린다.

### 3-3. 시간 처리
- 안정 판정은 **ESP32의 측정 시각**(uptime_ms끼리의 차이)으로 한다. 그래서 Wi-Fi 지연으로 데이터가 늦게 오거나 몰려와도 판정이 흔들리지 않는다.
- stale 판정은 **PC 시각**(monotonic)으로 한다. 두 시계를 서로 빼서 섞지 않는다.

### 3-4. 화면 표시 (GUI)
- 표시 전용으로 안정화한다(판단 로직과 무관).
  - 밀판의 작은 흔들림은 평활하고, 20mm를 넘는 움직임은 즉시 따라간다.
  - 상태 글자는 1초 이상 유지될 때만 바꾼다.
  - 메시지가 잠깐 끊겨도 마지막 위치를 유지한다.
- 고정 블록을 회색 빗금으로 그리고, 첫 캔을 실제 위치에 그린다.
- 상단에 보드 목록과 IP가 보인다(● 수신 중, ○ 끊김).

## 4. Wi-Fi 연결

### 4-1. 연결 방식
- ESP32는 **휴대폰 핫스팟에 손님(스테이션)으로 접속**한다. ESP32가 Wi-Fi를 만드는 방식이 아니다.
- Wi-Fi 이름과 비밀번호는 코드에 없다. `python tools/wifi_setup.py --port COMx --lane N`으로 USB를 통해 한 번 보내면 보드 내부 저장소에 저장되고, 이후에는 전원만 넣으면 자동으로 접속한다. 비밀번호는 화면이나 메시지에 표시되지 않는다.
- ESP32는 **2.4GHz만** 지원한다. 핫스팟 대역을 2.4GHz로 둔다.
- **PC도 같은 핫스팟에 연결**해야 받을 수 있다.
- Windows 방화벽에서 Python을 개인 네트워크에 허용해야 한다.

### 4-2. 전송 방식: UDP 브로드캐스트
- 각 보드는 자기 서브넷의 브로드캐스트 주소(예: 10.97.184.255) 포트 4210으로 보낸다. PC IP를 몰라도 되고, PC IP가 바뀌어도 그대로 받는다.
- USB로도 같은 줄을 동시에 보낸다(설정·진단용).
- 전원 대책
  - 처음 받은 보드의 공장 펌웨어가 Wi-Fi를 켤 때 전압 부족으로 재부팅을 반복했었다. 그래서 송신 출력을 11dBm으로 낮췄다.
  - 부팅 3초 뒤에 Wi-Fi를 시작하고, 직전 리셋이 전압 부족이면 30초 뒤에 시작한다.
  - 연결이 끊기면 10초마다 다시 시도한다. Wi-Fi가 없어도 측정과 USB 출력은 계속된다.

### 4-3. 측정한 지연과 손실 (1번 보드, 30초, USB 도착과 비교)
| 항목 | 값 |
|---|---|
| 지연 중앙값 | 약 64ms |
| 0.1~0.4초 지연 비율 | 약 45% (최대 약 418ms) |
| 손실 | 2.7% (다른 측정에서 4.5%, 가끔 한 번에 6~18개) |

- 원인(추정)
  - 브로드캐스트는 Wi-Fi 계층에서 수신 확인과 재전송이 없다.
  - 핫스팟이 절전 중인 기기를 위해 브로드캐스트를 모았다가 한꺼번에 내보낸다.
  - 2.4GHz 혼잡과 PC 블루투스 간섭이 있을 수 있다.
- 영향
  - 수량 정확도에는 영향이 없다(판정은 장치 측정 시각 기준).
  - 화면 반영이 최대 약 0.4초 늦어질 수 있다.
  - 5개 이하 누락은 기록만 하고 판정을 끊지 않는다. 그보다 크게 빠지면 해당 보드 레인의 안정 구간만 다시 시작한다.
- 대안(미적용): PC IP로 직접 보내는 유니캐스트로 바꾸면 재전송이 되어 지연과 손실이 줄 가능성이 있다. 대신 PC IP가 바뀔 때마다 보드 설정을 바꿔야 한다.

### 4-4. 여러 보드 동시 수신
- Python은 `device_id`별로 재부팅, 누락, 지연, 끊김을 따로 추적한다. 한 보드가 꺼지면 그 레인만 "보드 데이터 없음"(수량은 유지, 0으로 바꾸지 않음)이 되고, 다른 레인은 계속 동작한다.
- 두 보드가 같은 레인 번호를 보내면 `LANE_CONFLICT`를 기록하고 나중에 나타난 보드의 값은 쓰지 않는다.

## 5. 레인별 현재 상태 (2026-11-08)

| 레인 | 보드 | 상품 | 0개 / 1개 기준(허용 오차) | 2개 이상 | 비고 |
|---|---|---|---|---|---|
| 1 | `shelf-lane-1` | 맥주, 지름 65mm | 350(±10) / 328(±7) | 1개 위치 − 65mm씩 (추정) | 재생 검증에서 센서 값이 ±6mm 치우쳐도 정확 |
| 2 | `shelf-lane-2` | 칸타타 스위트 아메리카노 275ml, 66mm | 340(±6) / 329(±4) | 1개 위치 − 66mm씩 (추정) | 0↔1 간격 약 11mm, **여유 −2~+3mm로 작음** |
| 3 | `shelf-lane-3` | 미정 (설정은 예시값) | 미측정 | — | 센서 정상. 상품 정보와 0↔1 기록 필요 |
| 4 | 설치 중 | 미정 (설정은 예시값) | 미측정 | — | 펌웨어 업로드 완료. 마지막 확인 때 센서 `NOT_CONNECTED`, 배선 확인과 Wi-Fi 설정 필요 |

- 기준값은 레인마다 5분 기록(빈 상태 ↔ 캔 1개, 5회 반복)으로 정하고, 같은 기록을 프로그램에 재생해 오판이 없는지 확인했다.
- **센서나 표적이 움직이면 기준값을 다시 기록해야 한다.** 1번 레인은 배선 수리 중 센서가 약 9mm 움직여 다시 맞췄다.
- 설정 위치: `python/config.toml`의 각 `[[lanes]]`(`count_distance_mm`, `count_tolerance_mm`, `hysteresis_mm`, `median_window`)

| 로직 테스트 | `python -m unittest discover -s tests -t . -v` |

펌웨어 업로드는 `F:\arduino`에서 실행한다.
```
tools/arduino-cli/arduino-cli.exe upload -p COM7 --fqbn esp32:esp32:esp32 firmware/shelf_sensor
```
보드의 USB 칩 일련번호가 모두 같아서 어느 보드를 꽂아도 COM7로 잡힌다. **한 번에 한 대만** 연결해서 작업한다.

## 7. 남은 한계
- 거리만으로는 손이 표적을 오래 가리거나, 밀판을 오래 잡고 있거나, 상품이 걸린 경우를 완벽히 구분할 수 없다(재입고 모드로 일부 완화).
- 0개와 1개의 간격이 작은 레인(특히 2번)은 센서가 몇 mm만 움직여도 오판할 수 있다. 밀판 앞면에 5cm 스페이서를 붙이면 간격이 캔 지름만큼 커져 근본적으로 해결된다(미적용).
