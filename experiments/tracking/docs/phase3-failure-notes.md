# Phase 3 · tracker 실패 실험 기록

> 목적: ByteTrack 이 **언제 무너지는지**를 직접 확인하고 기록한다.
> 이 기록이 Phase 5(TAKE/RETURN 추론 방법 선택)의 근거가 된다.
> 근거: 문서 §6 Phase 3 — "ID switch 와 tracker 한계를 직접 기록"

## 실험 환경

| 항목 | 값 |
|---|---|
| 영상 | `data/videos/store-aisle-detection.mp4` (720x404, 59.9fps, 3921 frames) |
| 출처 | github.com/intel-iot-devkit/sample-videos (공개 데모 샘플) |
| 구간 | `--start-frame 1200 --max-frames 200 --stride 2` (원본 1200~1598, 약 6.6초) |
| 모델 | yolov8n.pt (pretrained), imgsz 640, conf 0.25, CPU |
| 처리 속도 | 6.6 FPS |

재현 명령:

```bash
python run_tracking.py --source data/videos/store-aisle-detection.mp4 \
  --start-frame 1200 --stride 2 --tracker-fps 30 --max-frames 200 \
  --out-dir outputs/store-aisle
python scripts/analyze_observations.py outputs/store-aisle/observations.jsonl --min-frames 10
```

### 확인 #1 — 성공: 장시간 ID 유지

track 1·2 는 약 6.6초(원본 398프레임) 동안 동일 ID 를 유지했다.
frame 1210 과 frame 1540 의 결과 영상을 비교하면 같은 사람이 ID 1, ID 2 를 그대로 달고 있다.
**Phase 2 의 완료 조건("같은 사람이 이동해도 일정 구간 동일 ID 유지")은 충족된다.**

### 확인 #2 — 실패: 가림/이탈 후 재등장 시 ID switch

track 3 → track 5 가 동일 인물이라는 근거:

| | 종료(track 3) | 시작(track 5) |
|---|---|---|
| 중심 x | 434.8 | 458.6 |
| bbox 너비 | 58.7 | 51.6 |
| frame | 1458 | 1558 |

거의 같은 위치·크기에서 끊기고 다시 생겼다. 공백은 **100 원본프레임 = 50 처리프레임 ≈ 1.7초**.

## 파라미터 변경 실험 — 결론: 튜닝으로 해결되지 않음

| 파라미터 | 값 | 고유 track 수 | 해석 |
|---|---|---|---|
| `lost_track_buffer` | 30 (기본) | 5 | 50 처리프레임 공백 > 버퍼 30 → track 파기 |
| `lost_track_buffer` | 90 | **5** | 버퍼를 3배로 늘려도 복구 실패 |
| `lost_track_buffer` | 150 | **5** | 5배로 늘려도 복구 실패 |
| `minimum_matching_threshold` | 0.95 | 5 | 최대한 관대해도 복구 실패 |
| `minimum_matching_threshold` | 0.9 | 5 | 동일 |
| `minimum_matching_threshold` | 0.5 | 11 | 더 엄격해져 track 파편화 |
| `minimum_matching_threshold` | 0.3 | 31 | 심하게 파편화 |

**주의 (문서화 오류 정정)**: `minimum_matching_threshold` 는 IoU 값이 아니라
**IoU 거리(1 − IoU)의 상한**이다. 즉 **값이 클수록 관대**하다. 낮추면 매칭이 엄격해져 ID 가 더 잘 끊긴다.

### 근본 원인

ByteTrack 은 **움직임(칼만 필터) + IoU 만으로 매칭하며 외형(appearance/ReID) 모델이 없다.**
1.7초 동안 대상이 보이지 않으면 예측 위치가 실제 위치에서 벗어나고, 겹침이 사라지므로
버퍼를 아무리 늘려도, 매칭을 아무리 관대하게 해도 같은 사람으로 이어붙일 수 없다.

## 이 프로젝트 설계에 주는 시사점 (중요)

현재 설계는 **track 단위로 `held_items` / `paid_items` / `unpaid_count` 를 누적**하고,
`unpaid_count >= 1` 인 track 이 `EXIT_APPROACH` 에 들어가면 HIGH_RISK 로 판정한다. (01 도메인 §4~7)

→ **고객이 선반 뒤로 가려졌다가 나오면 track_id 가 바뀌고, 누적된 미결제 상태가 통째로 사라진다.**
→ 상품을 집은 사람과 출구로 가는 사람이 서로 다른 track 으로 보여 **HIGH_RISK 가 탐지되지 않는다.**
→ 즉 이것은 tracker 의 사소한 품질 문제가 아니라 **위험 판정 로직의 전제를 무너뜨리는 문제**다.

### 다음 단계에서 검토할 대응 후보

| 후보 | 내용 | 비고 |
|---|---|---|
| ReID 기반 tracker | BoT-SORT + appearance embedding, DeepSORT | 어댑터만 교체하면 되므로 비용 낮음 (§4 구조의 이점) |
| track 병합 계층 | 끊긴 track 을 위치·시간·외형으로 사후 연결 | tracker 와 무관하게 TrackObservation 위에서 구현 가능 |
| 카메라 배치 | 가림이 적은 각도 / 다중 카메라 | 데이터 수집 단계의 선택 |
| 상태 이전 규칙 | track 소멸 시 미결제 상태를 일정 시간 보류 | 임시 완화책, 오탐 위험 |

**검증 비용이 가장 낮은 것은 ReID tracker 교체다.** `build_tracker()` 한 곳과
`TrackObservation` 변환만 새로 쓰면 되고, 같은 영상·같은 구간으로 위 표를 그대로 다시 채워 비교할 수 있다.

## 실험 #2 — 사람 교차 (people-detection.mp4)

> 영상: 768x432, 12fps, 596 frames. 전체 구간 처리 (`--tracker-fps 12`)

`scripts/find_crossings.py` 로 bbox 가 겹치는 구간을 먼저 찾았다.

| track 쌍 | 구간 | 최대 IoU |
|---|---|---|
| (2, 4) | frame 218~240 | 0.33 — 두 사람이 문 밖으로 나가버려 판정 불가 |
| (8, 10) | frame 354~401 | 0.20 — **판정 가능** |

### ByteTrack: ID 뒤바뀜 확인

frame 342 에 중심 x=408 (검은 옷 여성) 이던 **track 8 이 frame 365 에 중심 x=524 (흰 셔츠 남성)** 으로 옮겨갔다.
동시에 여성이 있던 자리(x≈413)에 **track 10 이 새로 태어났다.**

```
track 8: frame 343 cx=400.2  ->  frame 352 cx=502.1   (+102px, 9프레임)
track 10:                        frame 355 cx=413.4   (track 8 이 있던 자리)
```

`scripts/detect_id_jumps.py` 가 이 패턴을 자동으로 잡아낸다.

### 세 설정 비교

| tracker | 교차 전 (frame ~342) | 교차 후 (frame ~365) | 판정 |
|---|---|---|---|
| ByteTrack | track 8, 중심 408 | 중심 524 (**남성**) | ❌ ID 뒤바뀜 |
| BoT-SORT 기본 (0.5 / 0.25) | track 10, 중심 410 | 중심 438 (여성) | ✅ 유지 |
| BoT-SORT 개방 (1.0 / 0.5) | track 7, 중심 388 | 중심 438 (여성) | ✅ 유지 |

**BoT-SORT 는 기본 게이트만으로도 교차를 해결한다.** 교차 중에는 두 bbox 가 실제로 겹치므로
IoU 게이트(0.5)를 통과하고, 외형 비교가 정상 작동하기 때문이다.
즉 boxmot 의 기본 게이트 값은 원래 **교차 상황을 겨냥해 설계된 것**이다.

### 오병합은 발생하지 않았다

게이트를 연 설정(1.0 / 0.5)도 track 구조가 기본 설정과 동일했다
(20~77 / 180~249 에 2명 / 338~413 에 3명 / 523~559). **서로 다른 사람을 합치지 않았다.**

다만 이 영상은 **동시 등장 인원이 1~3명이고 옷차림이 뚜렷이 달랐다**(검은 원피스 / 흰 셔츠 / 체크 셔츠).
혼잡하고 비슷한 옷차림이 많은 실제 매장에서는 여전히 검증이 필요하다.

## 두 가지 실패는 서로 다른 문제다

| | **분열 (fragmentation)** | **뒤바뀜 (handoff)** |
|---|---|---|
| 증상 | 한 사람이 두 개의 ID 로 쪼개짐 | 한 ID 가 다른 사람에게 옮겨감 |
| 발생 | 오래 사라졌다 재등장 | 두 사람이 겹쳐 지나감 |
| track 수 | 늘어남 | **그대로** (그래서 개수만 세면 못 잡는다) |
| 탐지 도구 | `analyze_observations.py` 의 '끊김' | `detect_id_jumps.py` |
| 위험 방향 | 미결제 상태가 사라짐 → **미탐** | 미결제 상태가 남에게 옮겨감 → **오탐** |
| ByteTrack | ❌ | ❌ |
| BoT-SORT 기본 | ❌ | ✅ |
| BoT-SORT 개방 | ✅ | ✅ |

`scripts/detect_id_jumps.py` 로 교차 검증한 결과, store-aisle 의 실패는 '분열'로만 잡히고
'뒤바뀜'으로는 잡히지 않는다. 두 도구가 서로 다른 실패를 정확히 구분한다.

### 눈으로 확인

frame 2000(33.4초)과 frame 3400(56.7초)를 비교하면 청록색 상의 여성이 **23초 간격으로 동일한 ID 2**,
검은 옷 여성이 동일한 ID 6 을 유지한다. track 2 는 54초 동안 같은 사람을 놓지 않았다.

### 이 결과가 말해주는 것과 말해주지 않는 것

**말해주는 것**
- 65초 / 5명 동시 환경에서 track 이 폭증하지 않았다 (7개)
- ID 뒤바뀜이 한 건도 탐지되지 않았다
- 한 사람을 54초간 유지했다

**말해주지 않는 것**
- 등장 인물의 정답 수를 모른다. **서로 다른 사람을 합쳤어도 track 수는 줄어든다.**
  동시 5명 + 중간 교체를 감안하면 7개는 그럴듯하지만, 확정은 아니다.
- track 5 는 **11번 끊겼다가 복구**됐다. 복구에 성공했을 뿐, 시스템이 한계 근처에서
  동작 중이라는 뜻이다. 조건이 나빠지면 그 11번 중 하나가 실패로 바뀐다.
- track 7 은 1 프레임짜리 허위 track 이다.
