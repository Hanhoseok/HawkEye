# 카메라 2대 + 실시간 + 선반 센서 — 새 구조 설계

팀원 공유용 (2026-11-03). **설계 문서이고 아직 구현하지 않았다.**
지금 구조는 `docs/architecture.md`, 논문별 근거는 `docs/multiview-papers.md`(P1~P6), 한계 번호(A-1, C-4 …)는 `docs/limitations.md` 를 따른다.

## 1. 무엇이 바뀌나 — 한 문단

지금은 **카메라 1대 영상을 장면마다 ①→⑥ 한 줄로** 처리한다 (`src/pipeline.py`).
앞으로는 성격이 다른 카메라 2대를 **각자 따로 보고(①~④), 합친 다음(새 ⑦), 판단한다(⑤⑥).**

- **angle0 (선반 카메라)**: 선반 높이에서 선반을 정면으로 본다. 손·물건·상반신을 맡는다.
- **angle1 (전체 카메라)**: 높은 구석에서 매장 바닥 전체·계산대·문을 내려다본다. 동선·신원·결제·출구를 맡는다.
- **선반 센서**(나중): 칸별 무게 변화를 '선반 사건'의 또 다른 출처로 같은 자리에 넣는다.
- **판단 규칙**(집음·결제·절도)은 그대로 두고, 근거의 출처만 늘린다.

예시 손님 A 가 흰 상자 1개를 들고 계산대에 서지 않고 나가면 이렇게 처리된다.
1. angle0: "14:03:05 손님 a0-1 의 오른손목이 1단 3번 칸 상자에 닿음", 선반 지도는 "1단 3번 칸 비었음"
2. angle1: "그 시각 바닥 지도의 선반 앞 2번 자리에 w-1"
3. ⑦: a0-1 = w-1 = **매장 손님 1**. 1단 3번 칸 변화는 손님 1 것이다 (센서가 있으면 "1단 3번 -45g" 이 같은 시각에 확인).
4. ⑤: 집음 1개, 결제 0
5. ⑥: angle1 에서 손님 1의 발이 출구 → 문 밖으로 가면 **HIGH_RISK**

## 2. 우리 영상에서 잰 것 (2026-11-03)

### 2-1. 2차 촬영 영상 (`source/1(angle0)`, `source/1(angle1)`, 저장소 밖)

| | angle0 | angle1 |
|---|---|---|
| 편수 | 38 (C 17 · N 12 · T 9) | 38 (같은 이름으로 짝지음, 예: `20261028_N1` ↔ `N01`) |
| 형식 | 1920×1080, **30 FPS**, H.265 | 1920×1080, **60 FPS**, H.265 |
| 구도 | 선반 높이·정면. 선반 물건(병·샌드위치 상자)이 크게 보임, 오른쪽에 계산대·문 일부 | 매장 뒤쪽 높은 구석에서 문 쪽으로 내려다봄. 바닥 타일·통로·계산대·문·테이블. 선반은 옆면만 보임 |
| 1차 촬영(`source/0`, 40편)과 비교 | 1차는 선반에서 멀리 떨어진 정면 화각이었다(물건이 작고 흰 물건을 못 잡음, D-14). angle0 은 훨씬 가깝다 | 1차에 없던 높은 시점 |

### 2-2. 사람·발·물건이 얼마나 보이나 (YOLOv8n 그대로, 초당 10장)

| 측정 | angle0 | angle1 | 뜻 |
|---|---|---|---|
| 사람 키 (화면 비율 중앙, N1) | 0.91 (약 986px) | 0.57 (약 621px) | 둘 다 크기 기준 65px(B-3)보다 훨씬 큼 |
| 상자 아래가 화면 끝(≥0.98)인 비율 | **98%** (N1), 77% (C3) | **6%** (N1), 11% (C3) | **angle0 은 발이 안 보인다** → 바닥 위치·발 기준 구역 판단 불가. angle1 은 발이 보인다 |
| 사람 없는 첫 장면 물건 탐지 (1280, 점수 0.15 이상) | **11개**: 병 5개(0.43~0.78, 폭 44~61px), 샌드위치 2, 컵·그릇 등 | 2개: 싱크대(0.53), 책(0.17). 상품 없음 | **선반 지도는 angle0 에서만** 의미가 있다 |
| 한 명 영상(N1)에서 사람 2명 이상 잡힌 장면 | 0 / 186 | **19 / 184** | angle1 오탐 두 종류. 문으로 들어오는 사람이 위쪽 가장자리에서 두 상자로 쪼개짐, 그리고 **오른쪽 의자 위 외투를 사람으로 잡음**(x 0.72~0.88, y 0.24~0.51, 점수 0.30~0.33) |

### 2-3. 두 영상의 시간은 맞나

| 짝 | angle0 길이 | angle1 길이 |
|---|---|---|
| N1 | 18.6초 (559장) | 18.3초 (1101장) |
| T1 | 13.7초 (411장) | 14.0초 (842장) |
| C3 | 22.9초 (686장) | 23.1초 (1383장) |

- **초당 장면 수가 다르고(30/60), 녹화 시작·끝이 0.2~0.3초씩 다르다.** 같은 장면 번호가 같은 시각이 아니다.
- 사람 신호로 시차를 자동 추정해 봤다 (±3초 범위, 초당 10장).
  - "사람이 보이나" 신호: 최고 상관 시차 0.0초(N1)·+0.3초(C3), 상관 0.50·0.62
  - "움직임 속도" 신호: +1.5초, 상관 0.28
- **두 신호가 서로 다른 답을 내고 상관도 약하다 → 자동 추정만 믿을 수 없다.** 촬영 때 맞춤 신호(박수·시계 화면, `filming-guide.md` ②)가 필요하고, 그 신호를 찾아 시차를 기록하는 도구가 필요하다.

### 2-4. 두 사람 장면(C3)을 눈으로

- angle0: 검은 상의 두 사람이 **뒷모습으로 겹쳐** 선다. 뒤쪽 사람은 머리·어깨만 보인다.
- angle1: 같은 순간 둘이 **나란히** 보이고 바지(회색 청바지 / 어두운 바지)와 신발 색이 다르다.
- 1차 촬영 평가에서 두 사람 번호 뒤바뀜이 5편(C03·C06 확실)이었다 (`store-test.md` 3차). 높은 시점이 이 문제를 줄일 수 있다는 직접 근거다.

## 3. 설계 포인트 — 논문 근거 + 우리 근거 + 결정

### M-1. 카메라 역할을 고정해 나눈다

- **결정**: 판단마다 맡는 카메라를 정한다. 두 카메라가 같은 판단을 '투표'하지 않는다.

  | 판단 | 맡는 카메라 | 보조 |
  |---|---|---|
  | 매장 신원·동선·재입장 | angle1 | angle0 (선반 앞에서 외형 보강) |
  | 계산대 체류(결제)·출구·문 밖 | angle1 (발 위치 → 바닥 구역) | — |
  | 손 뻗기·손-칸 접촉 | angle0 (관절) | angle1 (선반 앞 바닥 자리에 머묾 = 기존 dwell) |
  | 선반 지도(무엇이 비었나) | angle0 | 센서 |

- **논문 근거**
  - P6: 위 화면은 전체 동선, 수평 화면은 외형. 두 화면은 상호 보완이다. 위 화면 추적 IDF1 80.2 > 수평 72.2 (가림이 드묾).
  - P3: 겹침이 적은 가장자리에서 정확도가 떨어진다 → 한 대만 보는 곳의 판단은 그 카메라가 맡는 편이 낫다.
- **우리 근거**
  - §2-2: angle0 은 발이 98% 안 보이고, angle1 은 상품을 하나도 못 잡는다.
  - B-9: 눈높이 카메라는 발이 안 보여 계산대·출구를 좌우 위치로만 갈랐다.
  - D-14: 먼 화각에서 흰 물건을 못 잡았다.

### M-2. 후기 융합 — 카메라별로 '관찰'만 하고, 합친 뒤에 '판단'한다

- **결정**: 카메라마다 지금의 ①②③④를 따로 돌려 관찰 기록(사람 상자·신원·손 접촉·선반 변화)을 낸다. 새 ⑦에서 합친다.
  ⑤⑥ 판단 층은 지금처럼 영상을 모르고 합친 기록만 받는다. 영상 특징을 바닥으로 투영해 신경망으로 함께 탐지하는 초기 융합(MVDet·EarlyBird)은 **1단계에 쓰지 않는다.**
- **논문 근거**
  - P3 §5: 초기 융합은 정확한 3D 정답·보정, **동기화된 카메라**, 한 기계의 큰 연산이 필요하다. 후기 융합은 카메라별로 따로 처리할 수 있고 시간 어긋남에 더 견딘다.
  - P2 Table 3: 카메라별 탐지 결과만 투영해도 MODA 68.2 (단순 묶기 11.3). 후기 융합도 쓸 만하지만 연결 단계가 성능을 좌우한다.
  - P2: 초기 융합이 크게 이기는 조건은 장면당 20~40명 혼잡이다.
  - P4: 판단은 모든 화면을 합친 뒤에.
  - P1: DMCT 도 카메라별 발 위치 열지도를 바닥에 투영해 합치는 방식이다.
- **우리 근거**
  - §2-3: 30/60FPS, 시작 시각이 다르다.
  - B-6: 보정이 없다.
  - G-1: GPU 를 못 쓴다.
  - 장면이 1~2명이라 혼잡이 아니라 비슷한 옷·겹침이 문제다 (C-4, C03·C06).
  - 기존 원칙: 층 사이는 `core/types.py` 형식만 주고받고, 판단 층은 영상을 import 하지 않는다 (`tests/test_contract.py`). 후기 융합이면 이 원칙을 그대로 넓힐 수 있다.

### M-3. 바닥 지도 — angle1 의 발 위치를 호모그래피로 옮긴다

- **결정**
  - angle1 바닥에서 점 4개 이상(바닥 타일 모서리 또는 종이 마커)을 찍어 **화면→바닥 3×3 호모그래피**를 구한다. 사람의 발 위치(상자 아래 가운데)를 바닥 좌표(cm)로 바꾼다.
  - **계산대·출구·문 밖 구역을 바닥 좌표 다각형으로** 다시 정의한다.
  - 선반 구역은 두 가지로 둔다.
    - angle0 화면 위의 선반 영역: 기존처럼 선반 지도용
    - 바닥 지도 위의 '선반 앞 띠': 누가 선반 앞에 섰나
  - **angle0 의 사람은 바닥에 투영하지 않는다.** 발이 안 보이기 때문이다. 대신 선반 앞 띠 위 좌우 위치(0~1)만 낸다.
- **논문 근거**
  - P2 식 2: 바닥(z=0) 위 점은 3×3 행렬 하나로 화면과 오간다. 이 투영은 발이 보여야 맞다.
  - P1 §4.2.1: DMCT 는 카메라별 발 위치를 호모그래피로 바닥에 옮긴다.
  - P1 §3.3: ArUco 마커로 보정한다.
  - P5 §V: 체스판·휴대폰 화면 정도의 간단한 보정으로 충분하다.
- **우리 근거**
  - B-6: 구역이 카메라 한 대 기준 화면 좌표다.
  - B-9: 발이 안 보이면 계산대·출구 판단이 약하다.
  - §2-2: angle1 발 보임 94%, angle0 2%.
  - 기존 규칙 "계산대·출구·문 밖은 **발 위치**로 판단"(`architecture.md` §3 ⑤)은 발이 보이는 angle1 에서야 제대로 작동한다.

### M-4. 교차 화면 연결 — 위치 관계가 1순위, 외형은 가림을 빼고 보조로

- **결정**: 새 `fusion/cross_view.py` 가 0.5초마다 angle0 의 화면 신원과 angle1 의 화면 신원을 짝짓는다.

  ```
  angle0 사람 i, angle1 사람 j, 최근 0.5초 조각에서
    위치 점수 = 두 화면이 함께 보는 선반 앞 구간에서
                angle0 좌우 위치(선반 앞 띠 0~1)와 angle1 바닥 위치를 선반 앞 띠에 내린 좌우 위치가
                가까운 장면의 비율  (사람이 2명 이상이면 좌우 순서도 맞아야 함)
    외형 점수 = OSNet 코사인 유사도 — 단, 그 장면에서
                다른 사람 상자에 70% 넘게 덮였거나, 화면 가장자리(2%)에 걸렸거나, 키 65px 미만인 사진은 뺌
    점수 = w × 위치 + (1 − w) × 외형      (외형을 쓸 수 없으면 위치만)
    헝가리안 매칭, 기준 미달이면 '짝 없음'(한쪽 화면에만 있는 사람) 허용
    조각 사이에는 같은 짝을 우선 유지 (한 조각의 흔들림으로 바꾸지 않음)
  ```

  - w 와 기준값은 **N 영상으로 정하고 고정한 뒤 C·T 로 채점**한다 (1차 촬영과 같은 방식).
- **논문 근거**
  - P6 Table 3: 화면 사이 위치 근거를 빼면 CVIDF1 84.0 → **15.5**, 외형을 빼면 82.6. 짧은 조각 + 빈 노드. 섞는 비율에 민감하지 않다 (Table 4, w1=0.3).
  - P4 Table 4: 외형 + 가림 처리로 IDF1 98.7·바뀜 0. 위치만이면 93.8·90번. 70% 넘게 가리면 외형 가중치 0.
  - P3 §3.5: 외형 + 위치 결합, 남은 것은 거리로 2단계 매칭.
  - P1: Retail 은 배경이 어수선해 재식별이 가장 어렵다 (mAP 28.5).
- **우리 근거**
  - C-4: 흰 티 2명 4편 중 1편만 버팀.
  - §2-4: 검은 상의 2명이 angle0 에서 겹친다.
  - E-4: 신원 확인 0.76 vs 기준 0.78 로 아슬아슬하다.
  - C-8: 가장자리 사진끼리는 누구든 0.71~0.83.
  - C-19: 잘린 사진이 평균에 섞인다.
  - 기존 키 65px 규칙.
  - 위치 1순위가 맞다는 근거가 우리 쪽에도 있다. 외형만으로 같은 손님을 잇는 신원 계층은 1차 40편에서 '나중에 합치기'가 한 번도 일어나지 않았다 (`store-test.md` 3차).

### M-5. 매장 신원은 angle1 이 기준이고, angle0 은 거기에 붙는다

- **결정**
  - 매장 손님 번호(store_id)는 angle1 의 화면 신원에서 만든다. angle0 화면 신원은 M-4 짝을 통해 그 번호를 받는다.
  - angle0 에서 가려졌다 나타나거나 화면 밖에 나갔다 들어와도, 그동안 angle1 이 계속 본 사람이면 같은 번호다.
  - 재입장은 angle1 이 문을 보므로 angle1 의 신원 계층(기존 `IdentityRegistry` 를 카메라별로 하나씩)이 먼저 잇는다.
  - 두 화면 모두에서 사라졌을 때만 '잃음'으로 본다. 기존 30초 보관 규칙은 그대로 둔다.
- **논문 근거**
  - P6 Fig. 6: 수평 화면에서 가려지거나 화면 밖에 나간 사람을 위 화면 번호로 되찾는다. 수평 화면 IDF1 58.1 → 72.2.
  - P3: 잃은 추적을 보관했다가 잇는다 (10단계).
- **우리 근거**
  - C-6·C-18: 재입장 4건 중 2건만 이어 붙임. 다시 들어오는 순간은 늘 화면 가장자리라 즉시 판정을 건너뛴다.
  - C-16: 한 사람만 가려지는 상황을 검증하지 못했다.
  - C-1: 3초 넘게 안 보이면 추적 번호가 쪼개진다.
  - §2-2: angle1 은 사람이 문으로 들어오는 순간부터 보인다.

### M-6. 손 뻗기를 '손목이 어느 물건 칸에 닿았나'로 바꾼다

- **결정**
  - **1단계 (학습 없음)**: angle0 에서 YOLOv8n-pose 로 손목을 찾는다. 손목이 선반 지도의 **물건 칸 상자**(④가 이미 만든다) 안에 0.3초 이상 들어가면 "손-칸 접촉" 사건으로 기록한다 (기준값은 N 영상으로 정함).
    기존 머묾(dwell)은 angle1 바닥의 선반 앞 띠에서 계속 계산해 **보조 근거**로 둔다. 손목이 안 보이는 장면을 메운다.
    천장용 `reach` 는 MERL 용으로 남긴다.
  - **2단계 (학습·보정)**: 선반 앞은 두 카메라가 함께 보므로 손목을 **삼각측량해 3D 로** 만든다. 1~3초 창의 골격 행동 모델(집음/놓음/만짐)을 몇 개 예시로 학습한다.
  - 어느 단계든 **행동 판단에는 물체 근거(선반 지도·센서)를 함께 쓴다.** 골격만으로 결정하지 않는다.
- **논문 근거**
  - P5: 여러 화면 골격으로 행동 인식 오류가 절반 넘게 줄었다. 대충 보정·동기화 없이도 이득이 있었다. 1~3초 창 92.8~95.7, 5개 예시 84.9. **골격만으로는 물체 행동을 헷갈려 물체를 함께 넣으라**고 제안한다 (부록 D).
  - P4: 관절이 두 화면 이상에서 보이면 3D 가 정확하다. 판단은 합친 뒤에.
- **우리 근거**
  - D-1: 머묾은 구경과 집기를 못 가른다. C 17편 중 11편 거짓 경보.
  - store-test 3차: 1~2.5초 짧은 집기를 놓쳤다 (21/25).
  - B-2: 손목 규칙은 천장 화각 전용이다 (비스듬한 화각에서 F1 0.15).
  - D-8: 자세만으로는 AUC 0.77.
  - D-16: 관절만 0.60, 손 사진 0.71.
  - §2-2: angle0 사람 키 약 986px 라 손목·손이 크게 보인다.
  - D-11: 선반 앞 두 사람의 변화를 누구에게 붙일지 못 정했다 → 손목이 닿은 칸이 그 답이 된다 (M-7).

### M-7. 선반 사건을 '칸 + 시각 + 출처'로 통일하고, 주인은 손목·바닥 위치로 정한다

- **결정**
  - 선반 지도의 자리 번호("1단 3번째")를 **칸 번호(slot)** 로 고정한다. 센서도 같은 칸 번호를 쓴다.
  - 선반 변화 기록에 **출처**(`vision` / `sensor`)와 **확신도**를 붙인다.
  - 변화의 주인을 정하는 순서를 바꾼다.
    1. 그 시각 그 칸에 손목이 닿은 사람 (M-6)
    2. 없으면 그 시각 바닥 선반 앞 띠의 그 칸 앞에 선 사람 (angle1)
    3. 둘 다 여러 명이면 지금처럼 '누구 것인지 모름'
  - 지금 규칙("가린 사람이 1명일 때만")은 3순위로 내려간다.
- **논문 근거**
  - P5 부록 D: 물체 위치를 골격과 같은 좌표로 맞춰 행동 판단에 함께 넣는다.
  - P4: 누가 누구를 가리는지 위치로 계산해 근거를 고른다.
- **우리 근거**
  - D-11: 두 사람이 선반을 함께 가린 C 영상 다수에서 변화를 못 붙였고, 머묾만 남아 거짓 경보가 났다.
  - D-17: 선반 기록이 틀리면 실제 집기를 지운다. 1차 T 6편이 이 이유였다 → 출처·확신도가 있으면 약한 시각 근거로 집기를 지우지 않게 할 수 있다.
  - D-12: 겹친 물건은 셀 수 없다 → 센서가 메운다.

### M-8. 센서는 '선반 사건'의 두 번째 출처이고, 정답을 자동으로 만드는 장치다

- **결정**
  - 센서 입력은 카메라와 같은 자리(⑦-b 선반 사건 묶기)로 들어온다. 형식은 `칸, 시각, 무게 변화(g), 확신도`.
  - 묶는 규칙
    - 시각 근거와 센서가 같은 칸·±1초 안이면 **확인**
    - 센서만 있으면 '센서만' 근거로 집음/놓음
    - 시각만 있으면 지금과 같음
    - 둘이 반대면 REVIEW
  - 판단 층은 출처 종류만 늘어나고 규칙 구조는 그대로다.
  - 센서 기록은 상품 모델·행동 모델의 **학습 정답**으로 쓴다. 사람은 센서와 영상이 어긋난 것만 확인한다.
  - 센서가 오기 전에는 **가짜 센서 기록 파일(CSV)** 로 ⑦-b 를 시험한다.
- **논문 근거**
  - P1: 보정된 깊이 센서로 3D 추적을 자동으로 만들고 사람은 틀린 것만 고쳐, 비용을 약 1/800 으로 줄였다. 한 명이 5시간 안에 고쳤다. 품질은 IDF1 100.
  - P3: 후기 융합은 출처마다 따로 처리하고 중앙에서 합친다 → 센서도 같은 방식으로 붙는다.
- **우리 근거**
  - 정답을 지금은 전부 눈으로 적는다 (`labels/store01/truth_functions.md`, A-10·A-11).
  - D-12·D-14: 겹친 물건·작은 흰 물건을 시각으로 못 센다.
  - F-4: `taken` 이 '물건 수'를 뜻하게 된 변경을 아직 팀에 공유하지 않았다 → 센서가 붙으면 개수 근거가 더 명확해진다.

### M-9. 공통 시계와 실시간 입력

- **결정**
  - 모든 장면·센서 기록에 **실제 시각(wall_ms)** 과 **카메라 이름(camera_id)** 을 붙인다.
    녹화본은 '영상 시작 시각 + 재생 위치 + 그 짝의 시차'로, 실시간은 받은 순간의 시계로 정한다.
  - 짝마다 시차를 `labels/<촬영>/sync.csv` 에 기록한다. 이를 위한 도구 `scripts/sync_pair.py` 를 만든다. 박수(소리)·시계 화면을 찾아 맞추고, 사람이 보고 확정한다.
  - 30/60FPS 차이는 시각 기준으로 처리한다. 장면 번호로 맞추지 않는다.
  - 합치기 규칙은 ±0.5초 어긋남을 견디게 만든다 (조각 단위 연결).
  - 실시간 입력
    - 카메라마다 읽기 스레드를 둔다.
    - **최신 장면만** 처리하고 밀린 장면은 버린다.
    - 끊기면 재연결한다.
    - RTSP 주소를 받는다.
- **논문 근거**
  - P3 §5: 초기 융합은 동기화가 필수이고, 후기 융합은 시간 어긋남에 더 견딘다.
  - P5 §V·부록: 동기화 없이 장면 수만 맞춘 대충 정렬로도 이득이 있었다.
  - P6 §4.1: 두 영상을 손으로 시간 맞췄다.
  - P1: 모든 스트림을 시간 동기화해 녹화했다.
- **우리 근거**
  - §2-3: 30/60FPS, 0.2~0.3초 길이 차이. 자동 추정 신호가 약하다 (상관 0.28~0.62, 서로 다른 답).
  - F-5: RTSP 주소를 받지 못한다.
  - F-6: 끊기면 종료하고 지연이 쌓인다.
  - B-5: 녹화본 시각 정보를 믿을 수 없는 경우가 있다.

### M-10. 평가 — 교차 화면 지표와 바닥 거리 기준을 더한다

- **결정**: 지금의 기능별 채점(사람 수·신원·손 뻗기·선반·절도)은 유지하고 세 가지를 더한다.
  1. 두 카메라 같은 사람 맞히기 **CVIDF1·CVMA**
  2. 바닥 위치 정확도 (0.5m 안이면 정답)
  3. 바닥 추적 IDF1 (1m 기준)

  정답은 **angle1 바닥 지도에서만** 적고, angle0 의 짝은 시각·위치로 옮겨 적는다.
- **논문 근거**
  - P6 식 9·10: CVIDF1·CVMA
  - P2·P3: 0.5m 기준 MODA
  - P1: 1m 기준 IDF1/MOTA
  - P1: 3D 에서 한 번 라벨링해 모든 화면으로 투영한다
- **우리 근거**
  - 지금 C 채점은 편 단위('깨끗함 9/17')라 얼마나 자주 틀리는지 모른다.
  - A-10: 정답 인원수를 사람이 확정하지 않았다.
  - 2차 촬영 38쌍은 정답표가 아직 없다 (A-13).

- **우리 근거**

### M-12. 연산 배분 — 무거운 일은 맡은 카메라에서만, 필요할 때만

- **결정**

  | 일 | 어디서 | 빈도 |
  |---|---|---|
  | 사람 탐지·추적 (640) | 두 카메라 | 매 처리 장면 (angle1 60FPS 는 15FPS 로 솎음) |
  | 관절 (YOLOv8n-pose) | angle0 만 | 선반 앞에 사람이 있을 때만 |
  | 물건 탐지 (1280) | angle0 만 | 지금처럼 '필요할 때만' (가린 동안 건너뜀, 한가하면 3장에 1번) |
  | OSNet 외형 | 두 카메라 | 지금처럼 새 번호 + 0.5초에 한 번, 가림·가장자리 사진 제외 |
  | 합치기 ⑦ | 중앙 | 0.5초 조각마다 (가벼움) |

  - 목표: 카메라당 실제 처리 5FPS 이상. 못 미치면 해상도 낮추기 → stride → OpenVINO 순서로 시도한다.
- **논문 근거**
  - P3 §5: 초기 융합은 한 기계에 연산이 몰리고, 후기 융합은 카메라별로 나눠 처리한다.
  - P4: 가벼운 백본(MobileNetV2)으로 5화면 15FPS.
  - P5: 행동 모델은 2~4.5M 로 실시간 가능.
  - P2: 입력을 720×1280 으로 줄여도 충분했다.
  - P6: CPU 1.74FPS. 무거운 최적화는 실시간과 거리가 멀다.
- **우리 근거**
  - G-2: 720p 추적만 BoT-SORT 5.9FPS.
  - 1080p 약 3FPS (`architecture.md` §4).
  - G-3: 선반 확인을 '필요할 때만'으로 바꿔 4.8 → 10~11FPS.
  - G-6: 사람(640)과 물건(1280)을 따로 탐지.
  - §2-2: 두 카메라 모두 사람이 커서(621~986px) 640 입력으로 충분하다.

### 5-11. 바뀌지 않는 것

- 판단 규칙의 뼈대: 집음 = 칸이 비었음, 결제 = 계산대 체류, 경보 두 단계, 일부 결제 = REVIEW.
- 기준값을 **정상 영상으로 정하고 고정한 뒤** 다른 영상으로 채점하는 평가 방식.
- 층 사이는 `core/types.py` 형식만 주고받고, 판단 층은 영상을 모른다.
- 영상·가중치는 저장소에 올리지 않는다. API 키는 환경변수.
- 카메라 1대로도 돈다. angle1 만 있으면 선반 근거 없이(동작만) 지금 수준으로 동작한다.
