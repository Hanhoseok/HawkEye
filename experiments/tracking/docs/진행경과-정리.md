> 대상: 팀원 공유용. 원본 맥락 문서(`절도위험탐지_1차구현방향_맥락공유`) 이후 달라진 내용을 정리한다.

## 2. Phase 3 — ByteTrack이 막힌 두 지점

### 실패 A. 분열(fragmentation) — 사라졌다 나타나면 ID가 쪼개진다

| track | 등장 | 소멸 | 길이 | 끊김 |
|---|---|---|---|---|
| 1 | 1200 | 1596 | 197 | 1 |
| 2 | 1200 | 1598 | 200 | 0 |
| 3 | 1200 | 1458 | 129 | 1 |
| 4 | 1558 | 1598 | 21 | 0 |
| 5 | 1558 | 1598 | 21 | 0 |

**track 3과 track 5가 동일 인물**이라는 근거:

| | track 3 종료 | track 5 시작 |
|---|---|---|
| frame | 1458 | 1558 |
| 중심 x | 434.8 | 458.6 |
| bbox 너비 | 58.7 | 51.6 |

공백 = 100 원본프레임 = **50 처리프레임 = 1.67초**.

**중요**: 가림이 곧 실패는 아니다. 짧은 공백은 복구된다.

| 사라진 시간 | 결과 |
|---|---|
| 0.03초 (track 3, frame 1436→1440) | 같은 ID 복귀 ✅ |
| 0.07초 (track 1, frame 1584→1590) | 같은 ID 복귀 ✅ |
| **1.67초** (track 3→5) | **새 ID 부여** ❌ |

(0.07초와 1.67초 사이 구간은 해당 사건이 없어 미측정)

### 실패 B. 뒤바뀜(handoff) — 겹치면 ID가 남에게 옮겨간다

`people-detection.mp4` 전체 596프레임(`--tracker-fps 12`) 처리:
414 detection / 339 observation / 7 track / 27.59 FPS

`scripts/find_crossings.py`로 찾은 겹침 구간:

| track 쌍 | 구간 | 최대 IoU | 판정 |
|---|---|---|---|
| (2, 4) | 218~240 | 0.33 | 두 사람이 화면 밖으로 나가 판정 불가 |
| (8, 10) | 354~401 | 0.20 | **판정 가능** |

측정 결과:

```
track 8 : frame 343 중심x=400.2  ->  frame 352 중심x=502.1   (+102px / 9프레임)
track 10:                             frame 355 중심x=413.4   (track 8이 있던 자리)
```

frame 342에 **검은 옷 여성**이던 ID 8이 frame 365에 **흰 셔츠 남성**에게 붙어 있고,
여성은 새 ID 10을 받았다. → **ID가 다른 사람에게 옮겨탐**.

### 두 실패의 차이

| | 분열 | 뒤바뀜 |
|---|---|---|
| 화면에 보이나 | 안 보임 | **둘 다 보임** |
| track 수 | 늘어남 | **그대로** (개수만 세면 못 잡음) |
| 탐지 도구 | `analyze_observations.py`의 '끊김' | `detect_id_jumps.py` |
| 위험 방향 | 미결제 상태 **소실** → **미탐** | 미결제 상태 **전이** → **오탐** |

### 튜닝으로는 해결되지 않았다

| 파라미터 | 값 | 고유 track |
|---|---|---|
| `lost_track_buffer` | 30 (기본) | 5 |
| `lost_track_buffer` | 90 | **5** |
| `lost_track_buffer` | 150 | **5** |
| `minimum_matching_threshold` | 0.95 | 5 |
| `minimum_matching_threshold` | 0.9 | 5 |
| `minimum_matching_threshold` | 0.8 (기본) | 5 |
| `minimum_matching_threshold` | 0.5 | 11 (파편화) |
| `minimum_matching_threshold` | 0.3 | 31 (심한 파편화) |

**문서화 오류 정정**: `minimum_matching_threshold`는 IoU 값이 아니라 **IoU 거리(1−IoU)의 상한**이다.
즉 **값이 클수록 관대**하다. 낮추면 매칭이 엄격해져 ID가 더 잘 끊긴다.

### 근본 원인

ByteTrack은 **칼만 필터 + IoU만으로 매칭하며 외형 모델이 없다.** 저장하지도 계산하지도 않으므로
설정으로 켤 수 있는 기능이 아니다. 대상이 오래 보이지 않으면 예측 위치가 어긋나 겹침이 사라지고,
겹쳐 있으면 좌표만으로는 두 사람을 구분할 근거가 없다.

## 3. 무엇을 어떻게 바꿨나

```
ByteTrack   = 칼만 예측 + IoU
BoT-SORT    = 칼만 예측 + IoU + 외형 임베딩(OSNet)
              +-- ByteTrack을 포함한다. "교체"보다 "추가"에 가깝다.
```

### 데이터 흐름 관점 — 어디가 바뀌었나

```
영상 -> 프레임 -> YOLO -> Detection -> [tracker] -> TrackObservation -> 로그/영상/분석
그대로    그대로   그대로     그대로       ★바뀜          그대로            그대로
```

| 단계 | 변화 | 근거 |
|---|---|---|
| 영상 입력 | **없음** | OpenCV, frame index + ISO8601 timestamp |
| YOLO 탐지 | **없음** | 같은 `yolov8n.pt`, conf 0.25, imgsz 640, person 필터. detection 571건으로 동일 |
| **tracker 입력** | **★ 바뀜** | 아래 |
| tracker 알고리즘 | 바뀜 | 외형 비교 단계 추가 |
| 출력 형식 | **없음** | `TrackObservation` 4필드 유지 |
| 로그·시각화·분석 | **없음** | 코드 미수정 |

**tracker 입력이 바뀐 지점** (이것이 유일한 입력 측 변화):

```python
# ByteTrack — 좌표만 넘김
self._tracker.update_with_detections(sv_detections)

# BoT-SORT — 좌표 + 원본 이미지 픽셀을 넘김
self._tracker.update(dets, frame.image)      # <- frame.image 가 추가됨
```

ByteTrack은 **숫자(좌표)** 만 보고 추적했고, BoT-SORT는 **숫자 + 그림(픽셀)** 을 본다.
외형을 판단하려면 bbox 안의 실제 픽셀을 잘라 임베딩을 뽑아야 하기 때문이다.
boxmot은 `update()`마다 고신뢰 detection 전부에 대해 임베딩을 계산한다(`botsort.py:174`).
**이것이 약 30% 속도 저하의 정체다.**

### 출력이 그대로인 것이 이번 작업의 성과

원본 문서 §4의 "ByteTrack → BoT-SORT로 바꿔도 뒤쪽 로직 유지"가 **주장이 아니라 실측**이 되었다.
tracker를 통째로 교체했는데 `pipeline.py`, `TrackObservation`, `observations.jsonl` 스키마,
분석 스크립트가 전혀 바뀌지 않았다. 교체 지점은 `build_tracker()` 한 곳뿐이다.
→ **Phase 4(인터페이스 고정) 완료**.

### 검토했으나 쓰지 않은 선택지

**ultralytics 내장 BoT-SORT**: `botsort.yaml`에 `with_reid` 옵션이 있으나,
`bot_sort.py`가 `with_reid=True`여도 `# Haven't supported BoT-SORT(reid) yet` 주석과 함께
`self.encoder = None`으로 둔다. 움직임 + GMC만 수행하므로 우리 문제를 해결하지 못한다.
(고정 CCTV라 GMC는 얻을 것도 없다 → `cmc_method=None`으로 비활성화)

## 4. BoT-SORT도 처음엔 실패했다 — 관문이 3개

기본 설정으로 돌렸더니 **ByteTrack과 결과가 완전히 동일(5개)** 했다.
원인은 직렬로 놓인 관문 세 개였고, 하나라도 막히면 나머지를 풀어도 실패한다.

```
[1] track이 아직 살아 있는가?      lost_track_buffer >= 공백 길이
      | 통과해야
[2] 외형을 비교할 자격이 있는가?    IoU 거리 <= proximity_threshold   <- 가장 큰 함정
      | 통과해야
[3] 외형이 충분히 닮았는가?         외형 거리 <= appearance_threshold
```

### 전체 시도 기록 (store-aisle frame 1200~1598)

| tracker | buffer | proximity | appearance | 고유 track | 판정 |
|---|---|---|---|---|---|
| ByteTrack | 30 | — | — | 5 | ❌ |
| ByteTrack | 90 | — | — | 5 | ❌ |
| ByteTrack | 150 | — | — | 5 | ❌ |
| BoT-SORT+ReID | 30 | 0.5 | 0.25 | 5 | ❌ |
| BoT-SORT+ReID | 30 | 1.0 | 0.25 | 5 | ❌ |
| BoT-SORT+ReID | 30 | 1.0 | 0.5 | 5 | ❌ |
| BoT-SORT+ReID | 90 | 0.5 | 0.25 | 5 | ❌ |
| BoT-SORT+ReID | 90 | 1.0 | 0.25 | 5 | ❌ |
| **BoT-SORT+ReID** | **90** | **1.0** | **0.5** | **4** | ✅ |

### 관문 2가 가장 큰 함정인 이유

boxmot `botsort.py:289-296`:

```python
ious_dists_mask = ious_dists > self.proximity_thresh
...
emb_dists[emb_dists > self.appearance_thresh] = 1.0
emb_dists[ious_dists_mask] = 1.0          # <- 안 겹치면 외형 정보를 버린다
dists = np.minimum(ious_dists, emb_dists)
```

기본값 0.5는 "IoU가 0.5 이상 겹칠 때만 외형을 본다"는 뜻이다.
오래 사라졌던 대상은 겹침이 0이므로 **외형 정보가 애초에 적용되지 않는다.**
→ **ReID를 켰다고 해서 가림 복구가 되는 것이 아니다.**

### 대조 실험 — 고친 것은 '느슨한 설정'이 아니라 '외형 정보'

성공 조합과 **완전히 같은 설정**에서 ReID만 껐을 때:

| 설정 | ReID | 고유 track | observation |
|---|---|---|---|
| buffer 90 / prox 1.0 / app 0.5 | **OFF** | 5 ❌ | 569 |
| buffer 90 / prox 1.0 / app 0.5 | **ON** | 4 ✅ | 570 |

→ 설정을 아무리 관대하게 풀어도 외형 정보 없이는 재식별이 불가능하다.
**"ByteTrack은 움직임만으로는 복구할 수 없다"는 진단은 설정 문제가 아니라 알고리즘의 한계가 맞았다.**

재현: `--tracker botsort --no-reid --lost-buffer 90 --reid-proximity 1.0 --reid-appearance 0.5`

### 병합이 올바른지 검증

| | 수정 전 | 수정 후 |
|---|---|---|
| track 3 | 1200~1458 (129 frames) | **1200~1598 (151 frames)** |
| track 5 | 1558~1598 (21 frames) | 사라짐 (track 3으로 흡수) |
| track 4 | 1558~1598 (21 frames) | **1558~1598 (21 frames) 유지** |

frame 1590에서 모자 쓴 남성이 다시 **ID 3**으로 표시되고(수정 전 ID 5),
좌하단에서 새로 진입한 다른 남성은 **ID 4로 분리 유지**되었다.
→ 합쳐야 할 것은 합치고, 합치면 안 되는 것은 합치지 않았다.

## 5. 교차 검증 (people-detection.mp4)

| tracker | 설정 | observation | 고유 track | 교차 전(frame ~342) | 교차 후(frame ~365) | 판정 |
|---|---|---|---|---|---|---|
| ByteTrack | — | 339 | 7 | track 8, 중심 408 | 중심 **524 (남성)** | ❌ 뒤바뀜 |
| BoT-SORT | 기본 0.5/0.25 | 400 | 7 | track 10, 중심 410 | 중심 438 (여성) | ✅ |
| BoT-SORT | 개방 1.0/0.5 | 404 | 7 | track 7, 중심 388 | 중심 438 (여성) | ✅ |

**BoT-SORT는 기본 게이트만으로도 교차를 해결한다.** 교차 중에는 두 bbox가 실제로 겹치므로
IoU 게이트(0.5)를 통과하고 외형 비교가 정상 작동한다.
즉 boxmot의 기본 게이트 값은 원래 **교차 상황을 겨냥해 설계된 것**이다.

**오병합 없음**: 게이트를 연 설정도 track 구조가 기본 설정과 동일했다
(20~77 / 180~249에 2명 / 338~413에 3명 / 523~559).
단, 이 영상은 동시 1~3명이고 옷차림이 뚜렷이 달라(검은 원피스 / 흰 셔츠 / 체크 셔츠)
오병합 검증으로는 약하다.

## 6. 속도 — 약 30% 저하

동일 조건(같은 구간 100 프레임, `--no-video`, 2회 반복)에서 따로 측정했다.

| tracker | 1회 | 2회 | 평균 |
|---|---|---|---|
| bytetrack | 8.47 FPS | 8.18 FPS | 8.33 |
| botsort | 5.76 FPS | 6.02 FPS | 5.89 |

→ **약 29~30% 저하.**

**주의**: 이전에 기록했던 "32%"는 영상 저장 여부가 섞인 부실한 비교였다.
각 실험 표의 FPS 값은 조건이 달라 tracker 간 비교에 사용하면 안 된다.

사람이 적은 구간에서는 임베딩 계산량이 줄어 훨씬 빠르다
(전체 영상 평균 15.75 FPS, 사람 2.9명 구간 5.9 FPS).

## 8. Phase 5 사전조사 — 측정으로 후보를 걸렀다

조사 구간: store-aisle frame 1200~1580 (20 간격, 20프레임), 사람 평균 2.9명

### A. 상품은 탐지되는가 → 된다

| 클래스 | 총 탐지 | 프레임당 평균 |
|---|---|---|
| bowl | 189회 | 9.4개 |
| refrigerator | 8회 | 0.4개 |
| cup | 6회 | 0.3개 |

비-person 객체 프레임당 평균 10.2개, 변동폭 8~12개(±25%).
COCO 사전학습만으로 이 매장의 상품이 잡힌다 → 별도 학습 없이 시작 가능.

### B. 손 위치는 잡히는가 → 잡힌다 (이 화각에서는)

`yolov8n-pose.pt`로 사람 56건의 손목 keypoint(COCO index 9, 10) 측정:

| 지표 | 값 |
|---|---|
| 손목 신뢰도 평균 | 0.63 |
| 손목 신뢰도 중앙값 | **0.69** |
| conf >= 0.5 비율 | 74/112 = **66%** |
| conf >= 0.3 비율 | 103/112 = **92%** |
| 사람 bbox 평균 높이 | **203px** (화면 404px 중 절반) |

**단서**: 이 영상은 사람이 화면의 절반을 차지한다. 천장에 높이 설치된 실제 CCTV는
사람이 훨씬 작게 잡히므로 이 수치는 그대로 적용되지 않는다. **카메라 배치 확정 후 재측정 필요.**

### C. 상품을 개별 추적할 수 있는가 → **안 된다**

파이프라인의 클래스만 `bowl`로 바꿔 그대로 추적(코드 수정 0줄).
구간 frame 1200~1398, 100 처리프레임 → 795 detection / 792 observation / 10 track.

| track | 관측 수 | 총 이동 | 한 프레임 최대 이동 | 해석 |
|---|---|---|---|---|
| 1~7 | 각 100 | **0.7 ~ 2.2px** | < 3.4px | 정지 상품, 완벽 추적 ✅ |
| 8 | 43 | 102.0px | **183.0px** | 이동량보다 점프가 큼 ❌ |
| 9 | 39 | 112.9px | 78.9px | ❌ |
| 11 | 10 | 333.6px | **325.7px** | 한 번에 순간이동 ❌ |

(비교: 같은 구간 person 추적 = 300 detection / 300 observation / 3 track)

**총 이동거리보다 단일 프레임 점프가 더 크다 = 상품이 움직인 것이 아니라
ID가 옆의 똑같은 그릇으로 건너뛴 것.**

그리고 이 문제는 **ReID로 해결되지 않는다.** 사람은 옷차림으로 구분되지만,
흰 그릇 A와 바로 옆 흰 그릇 B는 외형이 실제로 동일하기 때문이다.
**사람 추적에서 통했던 해법이 상품에는 원리적으로 통하지 않는다.**

### 후보 판정

| 후보 | 근거 | 판정 |
|---|---|---|
| Zone / 거리 규칙 | 사람 track 안정 확보. 선반 영역만 정의하면 즉시 가능 | ⭐ **baseline 채택** |
| Pose (손 keypoint) | 손목 conf 중앙값 0.69, 92%가 0.3 이상 | ⭐ 2순위 |
| 상품 추적·연결 | **측정 실패** (동일 상품 간 ID 건너뜀) | ❌ 주 신호 부적합 |
| HOI / Action Recognition / VLM | 미측정. 학습 데이터 또는 대형 모델 필요 | 보류 |

**Zone 규칙을 먼저 하는 이유는 성능이 아니라 다음 병목을 빨리 찾기 위해서다.**
TAKE/RETURN 다음에 상태 관리 → POS → 위험 판정이 남아 있는데, 그중 무엇이 진짜 어려운지 아직 모른다.
가장 단순한 판정으로 끝까지 한 번 이어보면 어디서 무너지는지 드러난다.

> **사라짐**: **3초까지만** — `lost_track_buffer: 90` = 30fps 기준 3초가 구조적 한계

### 미검증 (중요도 순)

1. **실제 CCTV 화각** — 모든 측정이 사람이 화면 절반(203px)을 차지하는 영상 기준.
   천장 설치 카메라면 사람이 작아져 IoU도 외형 임베딩도 불리해진다.
   **이것이 나머지 둘과 Pose 가능 여부, 선반 좌표까지 모두 좌우한다.**
2. **3초 넘는 긴 가림** — 고객이 선반 뒤에서 10초 상품을 고르는 상황.
   (🟢 갱신: 신원 계층이 10초 공백을 복원 — `identity-registry.md` §3-C. 분 단위는 미검증, `limitations.md` C-1·C-6)
   절도 탐지에서 가장 중요한 시나리오인데 현재 구조로는 못 버틴다.
3. **유사 복장에서의 오병합** — 혼잡은 검증됐으나 옷 색이 모두 달랐다.
   검은 패딩 다섯 명이면 외형 판단이 무력해진다.
4. 빠른 이동 (Phase 3 실험 #3) — 미실시
5. **탐지 자체의 실패** — tracker 이전 문제. ID 1이 상품을 집으려 웅크렸을 때 conf 0.41까지 하락.
   **상품을 집는 순간이 탐지가 가장 불안정한 순간**이라는 점이 이 프로젝트에서는 고약하다.
