## 지금 가장 큰 위험 (먼저 풀어야 할 것)

2026-11-10 에 다시 골랐다 (카메라 2대, 2차 촬영 38쌍 기준).

1. **집은 개수를 틀린다 (D-14·D-17·D-20)** — 사람이 적은 결제 라벨을 넣어도 30/38, 절도 4/9. 결제가 정확해도 집은 개수가 틀리면 판정이 틀린다.
   1차 평가부터 절도를 놓친 가장 큰 원인인데 상품 탐지 모델(설계 2-1)은 아직 시작하지 않았다.
2. **점수를 그대로 믿기 어렵다 (A-14·A-15)** — T·C 결과를 보며 규칙을 고쳤고, 판정이 안 나온 8쌍 중 6쌍이 맞음으로 세어지며, 경보가 맞는 사람에게 났는지는 보지 않는다. 절도 표본은 9쌍.
   (같은 날 채점 도구를 고쳐 정답표를 읽고 판정 없음을 따로 찍게 했다 — 판정이 나와서 맞은 것은 25쌍. 설정 고정·사람 단위·표본은 남음.)
3. **실제 결제 기록·선반 센서와 이어 본 적이 없다 (E-13·F-7)** — 결제는 '계산대에 서 있으면 결제' 아니면 사람이 적은 라벨, 센서는 가짜 기록뿐이다.
4. **실제 카메라로 실시간을 돌려 본 적이 없고 느리다 (F-1·G-9)** — 녹화본 흉내만 했다. 카메라당 초당 4~5장(목표 15장).

**2026-11-13 덧붙임 — 3차 촬영(39쌍, 후속 14~26 · 37~39) 뒤 달라진 것.** 위 목록을 다시 고른 것은 아니다.

- **3번 정정**: 3차에서 실제 선반 센서를 판정에 이어 봤다 — L1·L2 는 쓸 만하고(가짜 0, 놓침 11%) L3 는 못 쓴다(F-8). 결제는 바코드 삑 소리로 만든 라벨(F-7)이고 실제 결제 기록은 여전히 없다.
- **1번은 3차에서 더 뚜렷하다**: 영상만으로는 꺼냄 66개 중 5개만 판정 근거로 확인된다(A-17 · D-19 · D-22). 센서를 넣으면 절도 2 → 6/9.
- **새로 드러난 병목**: 두 사람 장면의 주인 정하기(D-11 — 센서를 넣자 정상 3편이 틀림), 결제 개수(E-10 · E-13 — T04·T05·T06 은 2·3차 모두 놓침), 되돌림 세기(D-23).
- **점수는 기록을 만든 컴퓨터에 따라 1쌍 다르다**(A-16): 3차 영상만 27/39(팀원 기록) · 26/39(이 컴퓨터).

**이전 목록 (2026-10-06 에 고른 것) — 그 뒤 어떻게 됐나**

1. **A-1 계산하고 나가는 손님을 통과시키는지 모른다** — 실제 영상으로 한 번도 확인하지 못했다. 촬영이 필요하다.
   → 🟡 1차 촬영 N01·N01-1 에서 결제 후 CLEAR 확인(10-14), 2차 촬영 정상 11/12. 결제는 계산대 체류로 본 것이라 실제 결제 기록으로는 아직(위 3번).
2. **B-1 우리 카메라의 설치 각도를 모른다** — 모든 수치가 다른 화각에서 나왔고, 파라미터는 화각을 넘지 못했다(B-2).
   → 1차(눈높이 1대)·2차(높은 전체 카메라 + 선반 카메라) 촬영으로 이 매장 화각에서 다시 쟀다. 실제 설치 위치·높이는 아직 미정(`multiview-design.md` §8), 바닥 보정점은 추정값(B-13).
3. **A-3 실제 CCTV 검증이 독립적이지 않다** — 두 편의 실패를 보고 규칙을 고쳤으니 그 두 편에서 맞는 것은 당연한 면이 있다.
   → 🔴 그대로. 같은 문제가 2차 38쌍에서도 생겼다(A-15).
4. **G-3 선반 확인을 켜면 실시간이 안 된다** — CPU 4.8 FPS.
   → 🟡 필요할 때만 탐지해 10~11 FPS(10-14). 카메라 2대는 합쳐 초당 약 9장(G-9).

- 한계를 새로 찾으면: 해당 분류 표 끝에 다음 번호로 추가한다. 근거 수치와 문서를 함께 적는다.
- 상태가 바뀌면: **행을 지우지 않는다.** 상태 기호를 바꾸고 '다음에 필요한 것' 칸에 날짜와 방법을 적는다
  (예: `🟢 2026-09-29 경보 두 단계 — ...`). 원래 문서의 '한계/남은 일' 항목에도 같은 표시를 붙인다.
- '지금 가장 큰 위험'은 상태가 바뀔 때마다 다시 고른다.
