# 선반 지도 — 어느 자리의 물건이 사라졌고, 그때 누가 있었나 (1단계)

## 목표

"집는 동작"을 세는 대신 **선반에서 물건이 몇 개, 어느 자리에서 줄었는지** 세어, 그때 선반 앞에 있던 손님에게 붙인다.

    손님 3 이 선반 앞에 섬 -> 손을 뻗음 -> 떠남
    선반 지도: 떠나기 전 [1단 1번째 병, 1단 2번째 스프레이, 1단 3번째 펌프병]
               떠난 뒤   [1단 1번째 병,                    1단 2번째 펌프병]
    -> "1단 2번째 스프레이가 사라짐 -> 손님 3"

이게 되면 지금의 약점 두 가지가 풀린다.
- 개수: 동작 수 ≠ 물건 수라서 REVIEW 를 따로 뒀다. 선반 개수를 세면 정확한 개수가 나온다.
- 되돌려놓기: 다시 놓으면 선반에 '생김'으로 나온다. 별도 감지가 필요 없다.

## 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| **1** | 선반 지도 + 전후 비교 + 손님에게 붙이기 (탐지는 일반 YOLO) | ✅ 이 문서 |
| **1-B** | 선반 확인 개수를 손님 기록(위험 판정)에 연결 | ✅ 아래 '손님 기록 연결' |
| **1-C** | 손 뻗기 + 선반 변화로 집음 / 놓음 / 만짐 판정 | ✅ 아래 '집음 / 놓음 / 만짐 판정' |
| 2 | 상품 탐지 모델 — 우리 상품으로 학습한 YOLO, 또는 SKU-110K 모델 + DINOv2 사진 비교 | 🟡 끼워 봄 (2026-11-19, 아래 '상품 모델을 끼워 봄') — 3차 39편에서 개수 맞음 7 → 34편. 기본 설정은 아직 일반 YOLO |
| 3 | 손님 장부를 "품목별 개수"로, POS 를 품목 단위로 대조 | |

## 동작 (`src/shelf/monitor.py`)

1. **선반 지도 확정** — 선반 앞에 아무도 없을 때 약 0.6~1초 동안 본 탐지를 모아,
   **대부분의 장면(60%)에서 보인 물건만** 확정한다(한두 장면만 튀는 오탐·누락 제거).
   높이로 단을 나누고 단 안에서 왼쪽부터 순서를 매긴다.
2. **가림** — 사람 상자가 선반 영역과 겹치면 그 장면으로는 세지 않고, 누가 가렸는지만 기록한다.
3. **비교** — 가림이 끝나면 새 지도를 만들어 **자리(위치)로 짝을 맞춘다**. 같은 종류가 여러 개여도 자리로 구별한다.
   종류 이름은 보조로만 쓴다(일반 YOLO 는 큰 통을 '변기'로 보는 등 이름이 자주 틀린다).
   짝이 없는 이전 물건 = 사라짐, 짝이 없는 새 물건 = 생김.
4. **확정** — 바뀐 상태가 관찰 시간만큼 더 유지돼야 확정한다. 손이 잠깐 가려 생긴 깜빡임을 거른다.
5. **손님에게 붙이기** — 가린 사람이 한 명이면 그 사람, 여럿이면 정하지 않는다, 아무도 안 보였으면 '모름'(손만 들어온 경우).

형식(`ShelfItem`, `ShelfChange`)은 실험 단계라 팀 공통 형식(`core/types.py`)에 넣지 않았다. 채택되면 팀에 공유한 뒤 옮긴다.

### 만들면서 고친 것

- **사람과 물건을 다른 해상도로 탐지** — 작은 물건을 잡으려고 해상도를 1280 으로 올리자, 가까이 있는 사람이
  조각 상자 4개(신뢰도 0.17~0.47)로 잡혀 한 명이 손님 5명이 됐다. 사람은 640(신뢰도 0.8 상자 하나)으로 따로 찾는다.
- **신원 유지(계층 2) 연결** — 추적 번호 대신 매장 단위 신원을 쓴다.
- **관찰 시간 0.6초** — 1초로는 사람이 떠난 뒤 영상이 끝나기 전에 확정하지 못했다(10566665: 떠난 뒤 1.8초).
- ultralytics 는 한 모델로 `predict` 를 두 번 부르면 앞 호출의 `classes` 설정이 남는다. 물건 탐지에도 찾을 종류를 매번 명시한다.

## 한계

- **영상 2편, 사건 2건**뿐이다. 동작을 확인한 것이지 정확도를 잰 것이 아니다.
- **일반 YOLO 라 작은 물건 탐지가 흔들린다.** 10566665 에서 아무도 없을 때도 물건 수가 4~6개로 오락가락했다. 2단계 상품 모델이 필요하다.
- **팔만 들어오면 주인을 정하지 못한다.** 실제 매장 카메라처럼 사람 전체가 보이면 생기지 않을 것으로 보지만 확인 전이다.
- **두 명이 동시에 선반에 있으면 정하지 않는다.** 손이 어디로 갔는지(손목 위치)로 가르는 것은 다음 과제다.
- 겹쳐 쌓인 물건, 뒤쪽에 숨은 물건은 셀 수 없다. 진열은 한 줄로, 서로 띄워야 한다.

## 손님 기록 연결 (1-B, 2026-10-06)

선반 지도의 결과를 위험 판정의 '가져간 물건 수'로 쓴다. 전체 파이프라인(`run_tracking.py --shelf ...`)에서 돈다.

    선반 방문 결과 (ShelfVisit)                       손님 기록
    "손님 3: 10~15초, 자리 2개 비었음"         ->  물건 +2, 그 시간의 집기 동작 1번은 대신함
    "손님 4: 20~26초, 변화 없음(구경)"          ->  물건 +0, 그 시간의 집기 동작은 지움
    "손님 5: 40~45초, 자리 1개 다시 참"         ->  물건 -1 (되돌려놓음)
    "누군지 못 정함: 자리 1개 비었음"            ->  아무에게도 안 붙임, 집기 동작 수 그대로

**가져간 물건 = 선반에서 확인한 개수(가져감 - 되돌려놓음) + 선반 기록이 없는 집기 동작 수.**
- 집기 동작은 '집었을 것 같다', 선반은 '실제로 줄었다'라서, 같은 시간·같은 선반이면 선반을 믿는다.
- '구경' 방문도 기록한다. 선반 앞에 서 있었지만 아무것도 안 바뀌었다는 것이, 그 시간 집기 동작이 헛것이었다는 근거다.
- 선반에 SHELF 구역 이름을 붙이면(`--shelf 이름=x1,y1,x2,y2@구역`) 그 구역의 집기 동작만 대신한다. 선반이 여럿이면 붙이는 게 안전하다.
- 선반을 지정하지 않으면 지금까지와 똑같다 (집기 동작 수, 문구도 '집기 행동 N번').
- 판정 문구에 근거가 붙는다: `물건 2개, 결제 없음 [선반 확인 2개 가져감, 구경만 1번]`.

**실제 영상 확인** (전체 파이프라인, BoT-SORT, stride 2):

| 영상 | 정답 | 결과 |
|---|---|---|
| 10566665 | 세탁 세제 병을 가져감. 중간에 큰 통을 들었다가 다시 놓음 | ✅ `2단 1번째 bottle 사라짐 -> 손님 1`, 손님 1 물건 1개. 들었다 놓은 큰 통은 세지 않음 |
| 10566653 (2026-10-06 추가) | 큰 통을 들었다 놓고, 두 번째 병을 바구니에 넣음 | ✅ `1단 2번째 bottle 사라짐 -> 손님 1`, 물건 1개. 들었다 놓은 통은 세지 않음 |
| 10566654 | 두 번째 스프레이를 가져감 (팔만 보임) | ✅ `1단 2번째 bottle 사라짐 -> 손님 1`. 1단계 시연(ByteTrack)에서는 팔이 두 번호로 나뉘어 주인을 못 정했는데, 파이프라인 기본 추적기(BoT-SORT)에서는 한 사람으로 이어져 붙었다 |

두 영상 모두 출구가 없어 최종 판정(HIGH_RISK 등)까지는 가지 않는다. 판정 규칙은 단위 테스트(`tests/test_shelf_count.py`)로 확인했다
— 한 번에 두 개, 구경만, 되돌려놓기, 선반 밖 집기, 주인 못 정함, 신원 합침, 선반 개수로 REVIEW.

**속도**: CPU 에서 13.8 → 4.8 FPS(10566665). 물건을 매 장면 전체 화면 1280 해상도로 찾기 때문이다.

**속도 개선 (2026-10-14)**: 물건 탐지를 필요할 때만 한다.
- 사람이 선반을 가린 동안은 건너뛴다 — 그 동안의 탐지는 원래 버리고 있었다(가려진 물건을 세면 틀리므로). 가렸는지는 사람 상자만으로 안다.
- 지도가 확정되고 아무 일 없으면 3장에 1번만 확인한다(`shelves.idle_every`). 누가 다녀간 뒤 비교할 때는 매 장면.

| 영상 | 예전 (매 장면) | 가린 동안 건너뜀 | + 한가할 때 3장에 1번 | 판정 |
|---|---|---|---|---|
| 10566665 | 4.8 FPS | 9.4 | **11.2** (탐지 80% 건너뜀) | 같음 (집음 1개, 2단 1번째) |
| 10566654 | — | 5.5 | **11.1** (58%) | 같음 |
| 10566653 | — | 8.4 | **10.3** (81%) | 같음 |

**화면 표시 (2026-10-14)**: `--show`/`--panel` 이면 선반 지도를 영상 위에 그린다 — 확정된 물건 자리(초록, '단-번째'),
선반 상태(초록 확정 / 주황 가림 + 누가 / 노랑 비교 중), 방금 사라진 자리(빨강 TAKEN)·생긴 자리(파랑 PUT). 상황판에도 선반 한 줄 요약.
실시간으로 쓰려면 선반 영역만 잘라서 찾거나, 선반 앞에 사람이 없을 때만 찾는 식으로 줄여야 한다(다음 과제).

**팀 공유 필요**: 선반을 켜면 경보의 `taken` 값이 '집기 행동 수'가 아니라 '가져간 물건 수(추정)'가 된다.
필드 이름·형식은 그대로라 경보 서버·앱은 고칠 것이 없지만, 뜻이 바뀌므로 `core/types.py` 설명은 팀에 공유한 뒤 고친다.

## 집음 / 놓음 / 만짐 판정 (1-C, 2026-10-07)

손 뻗기(집기 감지)와 선반 방문 결과를 합쳐 손님의 **행동**을 정한다 (`src/risk/customers.py` `ShelfAction`).

| 선반 방문 결과 | 그 시간 손 뻗기 | 행동 | 개수 변화 |
|---|---|---|---|
| 자리가 비었음 | 있음/없음 | **집음** | +비운 개수 |
| 자리가 다시 참 | 있음/없음 | **놓음** | −찬 개수 |
| 비기도 하고 차기도 함 | 있음/없음 | **자리 바뀜** | 순변화 |
| 그대로 | 있음 | **만지기만** | 0 |
| 그대로 | 없음 | 구경 | 0 |
| 선반 기록 없음 | 있음 | **확인 못 함** | +1 (지금처럼) |

- 근거를 함께 남긴다: `선반+동작`(둘 다 있음) / `선반만`(손 뻗기가 안 잡힘 — 팔만 보일 때 등) / `동작만`(선반 기록 없음).
- 손님의 물건 수 = 행동들의 개수 변화 합. 앞 절(손님 기록 연결)의 계산과 같은 값이다.
- 실행하면 방문이 끝날 때 `[행동] 손님 1: 집음 1개 — 사라짐: 2단 1번째 bottle (선반+동작)` 처럼 알리고,
  영상이 끝나면 최종 목록을 `actions.jsonl` 로 남긴다.
- 화면 알림과 최종 목록의 근거가 다를 수 있다. 손 뻗기(TAKE 후보)는 손님이 선반 구역을 떠난 뒤에 끝나므로
  방문이 먼저 확정되면 그 순간에는 `선반만`, 최종 목록에는 `선반+동작`이 된다(10566653 에서 실제로 나옴). **최종 목록이 기준이다.**

**실제 영상** (전체 파이프라인):

| 영상 | 정답 | 행동 판정 |
|---|---|---|
| 10566665 | 세제 병 집음 (큰 통은 들었다 놓음) | ✅ 집음 1개 — 2단 1번째 bottle (선반+동작) |
| 10566654 | 스프레이 집음 (팔만 보임) | ✅ 집음 1개 — 1단 2번째 bottle (선반만: 팔만 보여 손 뻗기가 안 잡힘) |
| 10566653 | 병 집음 (큰 통은 들었다 놓음) | ✅ 집음 1개 — 1단 2번째 bottle (선반+동작) |

**한계**
- **한 번의 방문 안에서 일어난 여러 행동은 순변화로만 보인다.** 세 영상 모두 '큰 통을 들었다 놓음'이 있었지만
  사람이 선반을 가린 동안이라 따로 보이지 않는다. 결과(집음 1개)는 맞지만 '들었다 놓음'은 기록되지 않는다.
- 선반 기록이 없으면 집음·놓음·만짐을 가를 근거가 없다(`확인 못 함`). 손 사진(손에 물건이 있나)으로 가르는 방법을 다음에 시험한다.
- 놓음·만지기만·자리 바뀜은 단위 테스트로만 확인했다 — 그런 장면의 영상이 없다(`validation-set.md` S-3~S-5).

## 상품 모델을 끼워 봄 (2단계, 2026-11-19)

물건 탐지를 일반 YOLO(`yolov8n.pt`)에서 우리 상품으로 학습한 모델(2차 yolov8n, GitHub 릴리스 `products-model-v2`)로 바꿔 3차 39편에 돌렸다.
선반 지도 코드와 기준값(`conf 0.05` · `map_score 0.15` · `stable_seconds 0.6`)은 **그대로**다 — 모델 파일만 바꿨다. 기본 설정은 아직 일반 YOLO 다.

### 돌린 방법

처음부터 다시 돌리지 않았다 (한 시간이 넘는다). 평가 저장분에서 선반 카메라의 물건 탐지만 새 모델로 다시 뽑아 넣고(`scripts/product_shelf_cache.py`, 장면 15,853장 · 약 1시간),

```bash

python scripts/product_shelf_cache.py --model $M --from dual_eval_shoot3 --out dual_eval_shoot3_prodcache
python scripts/dual_eval.py --shoot 3 replay --from dual_eval_shoot3_prodcache --out dual_eval_shoot3_prod --set shelves.model_path=$M
python scripts/product_shelf_report.py dual_eval_shoot3 dual_eval_shoot3_prod --rows --judge
```

### 약점

- **모델이 이 영상들로 학습했다.** 39편 중 25편은 학습에 쓴 영상이고, 선반의 처음 모습(상품 6개)은 영상마다 같다. 처음 보는 영상(검증 · 시험 14편)에서는 11편이 맞았다 (일반 YOLO 5편). 다른 날 · 다른 진열 · 다른 카메라 자리에서는 돌려 보지 않았다.
- **기준값을 손대지 않았다.** `conf` · `map_score` · `stable_seconds` 는 일반 YOLO 때 정한 값이다. 상품 모델에 맞춰 고르면 더 나아질 수도 있지만, 39편으로 고르면 39편에 맞춘 값이 된다.
- 주인이 정해진 것은 변화 54건 중 40건이다. 두 사람이 선반 앞에 함께 있으면 정하지 않는다 (1단계부터 있던 한계).
- 좋아진 5편 · 나빠진 3편 모두 한 번 돌린 결과다. 수가 작다 (39편).
- 저장분을 고쳐 돌렸다. 처음부터 돌린 것과 같은지는 한 편(C01)도 견줘 보지 않았다 — 물건을 처리한 장면 전부에서 찾았으므로 원래 실행(필요한 장면만)과 물건 탐지 입력은 같아야 한다.
- 속도는 재지 않았다. 같은 크기의 모델(yolov8n)을 바꿔 낀 것이라 달라질 까닭은 없지만 확인한 것은 아니다. 상품 탐지만은 한 장에 0.13초였다.
- 모델 파일은 저장소에 없다 (릴리스에서 받는다). 기본 설정을 바꾸면 모델 파일이 없는 컴퓨터에서 선반 지도가 안 돈다.
- 선반 지도는 상자의 자리로 센다. 푸셔 선반은 앞 상품을 꺼내면 뒤 상품이 앞으로 밀려 나온다 — N04 · T04 에서 하나 더 센 것이 이 때문인지 확인하지 못했다.
  - 갱신 2026-11-20 (기록을 열어 봄 — 사용자 질문): **개수가 틀린 5편은 모두 동과루 칸(L2, 3개가 앞뒤로 선 푸셔 줄)이 들어 있다.**
    선반 카메라는 이 줄을 앞에서 본다. 맨 앞 것은 온전한 상자(점수 0.85)로, 뒤의 둘은 앞 것 위로 삐져나온 윗부분만 작은 상자로 보인다 — 서로 겹치고 점수가 낮고(0.34~0.61), 2개인데 상자가 3~4개 나오기도 한다 (C01 · C18 은 동과루 상자 4개, C05 는 5개, N04 는 3개).
    앞 것을 꺼내면 뒤 것이 밀려 나와 **앞자리에는 여전히 상자가 있고**, 달라지는 것은 뒤쪽 작은 상자의 수뿐이다. 그 수가 깔끔하게 하나 줄면 맞게 세고(C01), 아니면 틀린다 — C18 은 1개를 꺼냈는데 '변화 없음', C05 는 2개 중 1개만, N04 는 1개인데 2개 사라짐.
    왜 그 수가 어긋나는지(겹친 상자를 하나로 모으는 단계인지, '약하게라도 보이면 사라짐이 아니다' 확인인지)는 코드를 따라가 확인하지 않았다.
    뒤 상품이 앞 상품에 완전히 가리는 진열이면 이 카메라로는 아예 못 센다 — 무게 센서(L1 · L2)나 줄을 옆 · 위에서 보는 카메라가 필요하다. 전체 카메라는 이 줄을 옆에서 봐서 동과루 3개가 나란히 보인다 (처음 진열을 39편 모두 맞게 셈, 점수 0.5 이상) — 그쪽 개수로 세어 보지는 않았다.

### 약점

- **판정에 안 쓴다.** 누가 들었는지(손님 번호)도 붙이지 않았다. 지금은 화면에 그리고 세기만 한다.
- **'들고 있다'가 '이 매장에서 꺼냈다'는 아니다** (N03). 전체 카메라에서 손에 든 상품을 봤다는 것만으로는 어디서 났는지 모른다 — 선반 지도(어느 칸에서 사라짐)와 맞춰 봐야 한다.
- '봤다'의 기준이 느슨하다 — 10초 안에 한 장면이라도 선반 밖에 그 종류의 상자가 있으면 본 것으로 셌다. 몇 장면 동안 이어서 보이는지, 계산대 · 출구까지 따라가는지는 세지 않았다.
- 모델이 이 영상들의 장면으로 학습했다 (39편 중 25편이 학습 영상). 학습 · 검증 · 시험으로 갈라 세지 않았다. 다른 날 · 다른 진열에서는 안 돌려 봤다.
- 점수 0.5 가 진열 개수를 39편 모두 맞힌다는 것은 이 39편을 보고 안 것이다 — 기준으로 삼으면 39편에 맞춘 값이다.
- 속도: 전체 카메라에도 돌리면 물건 탐지가 한 번 더 든다 (CPU 에서 한 장에 0.19초 — 초당 15장을 실시간으로는 못 따라간다).
- '선반 밖'은 처음 1초의 상자에 기대어 잡는다. 영상이 시작할 때 사람이 선반을 가리고 있으면 틀린다 (3차에는 그런 영상이 없다).

- **영상 전체의 차이만 봤다.** 언제 · 누가 꺼냈는지는 모른다. 중간 개수에는 사람이 가린 상태가 섞여 있다 (예: C02 는 (2, 3, 1) → … → (0, 0, 0) → (1, 2, 1)). 방문마다 세려면 전체 카메라에서 누가 선반을 가렸는지부터 알아야 한다 — 안 만들었다.
- **판정에 안 넣었다.** 점수가 어떻게 되는지 모른다.
- 겹침 0.4 · 0.6초는 이 39편을 보고 고른 값이다 (정상 영상만으로 고르지 않았다).
- 모델이 이 영상들로 학습했다. 처음 보는 14편에서는 13편.
- **전체 카메라가 줄을 옆에서 본다는 것은 지금 카메라 자리 덕이다.** 카메라를 옮기면 달라진다. 줄이 더 길거나 상품이 더 많으면 옆에서도 가릴 수 있다 — 3종 6개로만 봤다.
- 모델이 종류를 **자리로도** 배웠을 수 있다 (C16). 진열이 늘 같은 영상으로 학습했다 — 자리를 바꾼 영상은 C16 한 편뿐이라 확인하지 못했다.
- 영상이 끝날 때 사람이 선반을 가리고 있으면 끝 개수가 틀린다 (3차에는 그런 영상이 없었다).
- 속도는 그대로다 (CPU 한 장 0.19초). 개수만 세려면 가끔만 돌려도 될 텐데 재 보지 않았다.

## 전체 카메라 개수를 판정에 넣음 (2026-11-20)

선반 방문(선반 카메라가 정한 시작 · 끝 · 주인)은 그대로 두고, 그 방문의 **꺼냄 · 놓음 개수만** 전체 카메라가 센 상품 개수로 바꾼다.
기본은 꺼져 있다 (`fusion.overview_count`). 코드는 `src/fusion/overview_count.py`.

```bash
python scripts/product_overview_items.py --visits --out dual_eval_shoot3_prod            # 방문마다 세어 정답과 견줌
python scripts/dual_eval.py --shoot 3 judge --out dual_eval_shoot3_prod --set fusion.overview_count=true   # 판정에 넣어 채점
```

### 세는 법

1. 선반 자리 = 처음 1초에 본 상품 상자들을 감싼 네모 + 40픽셀.
2. 장면마다 그 안의 상품을 종류별로 센다 (같은 종류가 IoU 0.4 이상 겹치면 하나).
3. **사람 상자가 선반 자리와 겹친 장면은 '가림'** — 그때의 개수는 안 믿는다.
4. 가리지 않은 채 0.6초 넘게 그대로인 개수 = '본 개수'.
5. 방문마다 **전에 본 개수 - 뒤에 본 개수**. 종류별로 줄어든 것이 꺼냄, 늘어난 것이 놓음.
   - 전 = 방문 시작 전에 시작한 마지막 '본 개수'. 앞 방문이 끝난 뒤에도 보고 있던 것이어야 한다.
   - 뒤 = 방문이 끝난 때까지 이어진 '본 개수', 없으면 끝나고 3초 안에 처음 나온 것.
   - 방문의 끝은 1초까지 어긋나도 봐준다 (두 카메라가 보는 '가림'이 다르다). 시작은 안 봐준다.
6. 전이나 뒤를 못 봤으면 **선반 지도 개수 그대로** 쓴다. 센서 기록이 있는 방문은 센서 개수가 먼저다.
7. 방문이 없는 때의 개수 변화는 세지 않는다 (전체 카메라만으로는 꺼냄을 만들지 않는다).

판정은 뒤 개수가 나올 때까지 그 방문을 최대 3초 더 붙든다 (`fusion.overview_count_wait_seconds`). 그때까지 들어온 장면만 쓴다.

### 든 사람으로 주인 정하기 (`src/fusion/overview_count.py` `HolderTracker`)

- 전체 카메라 장면마다, **선반 자리 밖**에 보인 상품 상자가 누구 손에 있는지 적는다.
  손목이 가장 가까운 사람 (상품 상자 대각선의 1.5배 안). 두 사람 손목이 비슷하게 가까우면 안 적는다. 손목이 없으면 상품 가운데가 한 사람 상자 안에만 있을 때 그 사람.
- 묻는 때: 다른 근거(가린 사람의 짝 · 손-칸 접촉 한 명 · 선반 앞 한 명)로 **주인을 못 정한 방문**이고, 전체 카메라 개수가 **어느 종류가 줄었는지** 본 방문.

- 종류마다 든 사람이 다르면 방문을 **사람별로 나눈다** (각자 '꺼냄: 종류' 한 줄). 아무도 든 것을 못 봤으면 지금처럼 '모름'.
- 다른 근거로 주인이 정해진 방문은 안 건드린다.

## 3차 기준을 상품 모델 기록으로 옮김 (2026-11-20)

사용자 결정: 최종 판정은 **상품 모델 기록 + 센서 로그 + 결제 로그**로 낸다. 일반 탐지 모델 기록과 '선반 앞 머묾'은 그 전의 임시 단계다.
그래서 3차의 기준(회귀 검사 · 분석 도구의 '3차 촬영' · `dual_eval.py --shoot 3` 의 기본)을 상품 모델 기록으로 옮기고, 머묾을 3차 기본 판정에서 뺐다.

| 영상 | 정답 | 판정 | 원인 |
| --- | --- | --- | --- |

### 기록을 처음부터 다시 만들려면

상품 모델 파일(`training/products/handoff/products-model-v2/yolov8n_1280_v2.pt`)이 있어야 한다. 판정(`judge`)과 회귀 검사에는 필요 없다.

```bash
# 가. 예전 기록의 저장분에서 선반 물건 탐지만 바꾸기 (지금 기록을 만든 길, 십여 분)
M=training/products/handoff/products-model-v2/yolov8n_1280_v2.pt
python scripts/product_shelf_cache.py --model $M --from dual_eval_shoot3 --out dual_eval_shoot3_prodcache
python scripts/dual_eval.py --shoot 3 replay --from dual_eval_shoot3_prodcache --out dual_eval_shoot3_prod
python scripts/product_overview_items.py --model $M --from dual_eval_shoot3 --out dual_eval_shoot3_prod    # 전체 카메라 상품
# 저장분도 기본 기록 폴더에 둔다 (regress.py --replay 가 여기서 읽는다): <prodcache>/<짝>/cache → <prod>/<짝>/cache

# 나. 영상에서 처음부터 (한 시간 넘음)
python scripts/dual_eval.py --shoot 3 run --record-cache

```

`run` 은 상품 모델 파일이 없으면 그 자리에서 멈춘다. 전체 카메라 상품 기록이 없는 짝은 판정이 실패로 적힌다 (조용히 예전 방식으로 돌아가지 않는다).

```bash

    --set fusion.overview_count=false --set fusion.overview_owner=false --set fusion.overview_dwell=true    # 28 / 39
```
