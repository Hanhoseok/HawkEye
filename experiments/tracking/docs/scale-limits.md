# 스케일 한계선 — 사람이 얼마나 작아지면 무너지는가

> 목적: 카메라 화각을 미리 정하지 않고도 쓸 수 있는 **범용 설치 기준**을 만든다.
> 결론 먼저: 한계는 "화면 속 픽셀"이 아니라 **"모델 입력 텐서 속 픽셀"** 이며,
> 카메라 배치와 `imgsz` 두 가지 수단으로 똑같이 충족할 수 있다.

---

## 0. 왜 이 측정이 필요했나

처음에는 "실제 카메라 화각을 정한 뒤 거기서 재측정하자"고 판단했으나, 이는 틀린 전제였다.
**고정 카메라 한 대 안에서도 사람 크기가 계속 변하기 때문이다.**

store-aisle 전체 영상 6,559건의 사람 bbox 높이:

| | 값 |
|---|---|
| 최소 | 65px |
| 중앙값 | 203px |
| 최대 | 304px |
| **최대/최소** | **4.7배** |

같은 사람 한 명 안에서도:

| track | 최소 | 최대 | 배율 |
|---|---|---|---|
| 5 | 70px | 296px | **4.2배** |
| 8 | 65px | 272px | 4.2배 |
| 1 | 78px | 304px | 3.9배 |

통로 안쪽에 있을 때와 카메라 앞에 왔을 때가 4배 차이다.
**화각을 고정해도 스케일은 고정되지 않는다.** 따라서 특정 화각에 맞춰 튜닝하는 대신,
**어느 크기까지 버티는지를 재서 설치 기준으로 내놓는 것**이 맞다.

(덧붙여, 현재 설정은 이미 이 4.7배 범위에서 track 7개 · 뒤바뀜 0건을 냈다.
스케일 강건성이 어느 정도 확보되어 있다는 뜻이다.)

---

## 1. 실험 방법

`--scale` + `--scale-mode shrink` 옵션을 추가했다.

- **shrink**: 프레임 크기는 그대로 두고 **내용만 축소**해 가운데 배치.
  사람의 픽셀 크기와 디테일이 동시에 줄어든다 → **실제 원거리 촬영에 가깝다.**
- **resize**: 프레임 자체를 축소. 디테일만 손실되고 사람이 화면에서 차지하는 **비율은 그대로**.

### resize 모드는 왜 쓸모가 없었나 (방법론 기록)

처음에 resize 모드로 먼저 재봤더니 **180x101 까지 줄여도 detection 561건 / track 4개로 멀쩡**했다.
YOLO 가 어차피 입력을 `imgsz`(640)로 리사이즈하므로, 화면 비율이 유지되면
텐서 안에서 사람이 차지하는 크기가 변하지 않기 때문이다. 디테일(블러)만으로는 잘 안 무너진다.

**이 실패한 시도 자체가 힌트였다** — 진짜 변수는 화면 해상도가 아니라 텐서 속 크기라는 것.

### 측정 조건

| 항목 | 값 |
|---|---|
| 영상/구간 | `store-aisle-detection.mp4` frame 1200~1598 |
| 샘플링 | `--stride 2 --tracker-fps 30`, 200 처리프레임 |
| tracker | botsort + ReID (buffer 90 / prox 1.0 / app 0.5) |
| detector | yolov8n.pt, conf 0.25, CPU |
| 정답 | track **4개**, 그중 **3명**이 구간 전체(1200~1598)에 걸쳐 동일 ID 유지 |

원본 프레임 720x404 이므로 `imgsz` 640 기준 텐서 환산 계수는 **640/720 = 0.889** 이다.

## 2. 결과 — 스케일 스윕 (imgsz 640 고정)

| scale | 화면 속 사람 키 | **텐서 속 사람 키** | detection | 재현율 | track | 전 구간 유지 | 판정 |
|---|---|---|---|---|---|---|---|
| 1.0 | 203px | **180px** | 571 | 100% | 4 | 3명 | ✅ |
| 0.7 | 142px | **126px** | 552 | 97% | 4 | 3명 | ✅ |
| 0.5 | 102px | **90px** | 551 | 96% | 4 | 3명 | ✅ |
| 0.35 | 71px | **63px** | 470 | 82% | 4 | 3명 | ⚠ 열화 |
| 0.25 | 51px | **45px** | 245 | 43% | 4 | **1명** | ❌ |
| 0.18 | 37px | **32px** | 45 | 8% | 1 | 0명 | ❌ |
| 0.12 | 24px | **22px** | 0 | 0% | 0 | 0명 | ❌ |

- "화면 속 사람 키"는 중앙값 203px × scale 로 환산한 값이다.
  (실측 중앙값은 이보다 크게 나오는데, 작은 사람이 먼저 탐지에서 빠져
  큰 사람만 남는 **생존 편향** 때문이다. 이 편향 자체가 "작은 것부터 사라진다"는 증거다.)
- **track 수만 보면 0.25 까지 4개로 멀쩡해 보인다.** 하지만 "전 구간 유지 인원"이 3명 → 1명으로
  무너진다. **개수만 세면 붕괴를 놓친다.**

---

## 3. 검증 — 한계는 텐서 픽셀이다

위 표에서 세운 가설: *"진짜 제약이 텐서 속 크기라면, 화면 속 사람이 작아도 `imgsz` 를 키우면 회복돼야 한다."*

붕괴 지점인 **scale 0.25 (화면 속 51px)** 에서 `imgsz` 만 바꿔 재측정:

| imgsz | 환산 계수 | **텐서 속 사람 키** | detection | 재현율 | 전 구간 유지 | 속도 |
|---|---|---|---|---|---|---|
| 640 | 0.889 | **45px** | 245 | 42% | 1명 ❌ | 12.69 FPS |
| 960 | 1.333 | **68px** | 508 | 88% | **3명 ✅** | 7.26 FPS |
| 1280 | 1.778 | **91px** | 546 | 95% | **3명 ✅** | 5.43 FPS |

### 가설이 정확히 맞았다

두 실험(스케일 축과 imgsz 축)은 완전히 독립인데, **텐서 픽셀로 환산하면 같은 곡선 위에 놓인다.**

| 텐서 속 사람 키 | 재현율 | 출처 |
|---|---|---|
| 90px | 96% | scale 0.5 / imgsz 640 |
| **91px** | **95%** | scale 0.25 / imgsz **1280** |
| 63px | 82% | scale 0.35 / imgsz 640 |
| **68px** | **88%** | scale 0.25 / imgsz **960** |
| 45px | 43% | scale 0.25 / imgsz 640 |

화면 속 크기가 4배 달라도 텐서 속 크기가 같으면 결과가 같다.
→ **"카메라가 얼마나 머냐"가 아니라 "모델이 몇 픽셀을 보느냐"가 유일한 변수다.**

## 4. 설치 기준 (범용 스펙)

```
텐서 속 사람 키 = 화면 속 사람 키 × imgsz ÷ 프레임의 긴 변
```

| 텐서 속 사람 키 | 상태 | 권고 |
|---|---|---|
| **90px 이상** | 정상 (재현율 95%+, 신원 완전 유지) | ✅ **목표치** |
| 65~90px | 열화 시작 (82~88%) | ⚠ 허용 하한 |
| 45~65px | 붕괴 (43% 이하, 신원 유실) | ❌ |
| 35px 미만 | 사실상 탐지 불가 | ❌ |

**이 기준은 매장 구조·카메라 기종과 무관하게 적용된다.**
현장에서는 다음 한 줄로 확인할 수 있다:

> 매장에서 **가장 먼 지점에 선 사람**의 화면 속 키를 재고, 위 식으로 텐서 픽셀을 계산해
> **90px 이상**이면 정상, **65px 미만**이면 조치가 필요하다.

### 기준을 못 맞출 때의 수단 (비용 순)

| 수단 | 효과 | 비용 |
|---|---|---|
| `imgsz` 상향 (640 → 960 → 1280) | 텐서 픽셀 비례 증가 | **속도 12.7 → 7.3 → 5.4 FPS** |
| 카메라를 더 낮게/가깝게 설치 | 화면 속 픽셀 증가 | 화각이 좁아져 사각 발생 |
| 카메라 대수 증가 | 각 카메라 담당 구역 축소 | 비용 + 다중 카메라 신원 연결 필요 |
| 더 큰 detector (yolov8s/m) | 작은 객체 성능 향상 | 속도 추가 저하 (미측정) |
| 고해상도 카메라 | 화면 속 픽셀 증가 | `imgsz` 도 같이 올려야 의미 있음 |

**주의**: 고해상도 카메라만 쓰고 `imgsz` 를 640으로 두면 효과가 없다.
프레임이 커질수록 환산 계수가 작아져 텐서 속 크기는 그대로이기 때문이다.
(1080p + imgsz 640 은 720p + imgsz 640 보다 나을 것이 없다.)

## 4-B. 중대한 단서 — imgsz 는 원본 해상도까지만 의미 있다

위 스펙을 실제 CCTV 영상(CAVIAR, 384x288 쇼핑센터 복도)에 적용했더니 **효과가 없었다.**

| imgsz | detection | 탐지된 최소 사람 | 끊김 합계 | ID 뒤바뀜 |
|---|---|---|---|---|
| 640 | 1,993 | 15px | 22회 | 2건 |
| 1280 | 1,921 | 12px | **52회** | 2건 |

detection 은 오히려 줄고 **끊김은 2배 이상 늘었다.**

### 왜 store-aisle 에서는 되고 CAVIAR 에서는 안 됐나

| | 프레임 긴 변 | imgsz 640 일 때 | imgsz 1280 일 때 |
|---|---|---|---|
| store-aisle | **720px** | 720 → 640 **축소** (정보 버림) | 720 → 1280 확대 (정보 보존) |
| CAVIAR | **384px** | 384 → 640 이미 확대 | 384 → 1280 더 확대 (새 정보 없음) |

**store-aisle 에서 imgsz 를 올려 효과를 본 것은 "정보를 추가"해서가 아니라
"imgsz 640 이 원본을 640 으로 줄이며 버리고 있던 정보를 되찾아서"였다.**

CAVIAR 는 원본이 384px 이라 imgsz 640 시점에 이미 정보를 전부 쓰고 있었다.
1280 으로 올려봐야 보간(interpolation)일 뿐 새로운 픽셀 정보가 없고,
과도한 확대가 오히려 탐지를 불안정하게 만들어 끊김이 늘었다.

### 수정된 규칙

```
imgsz 는 프레임의 긴 변까지만 올릴 가치가 있다.
그 이상은 보간일 뿐이며, 실측에서는 끊김만 2배 이상 늘었다.
```

즉 앞 절의 "imgsz 상향"은 **만능 수단이 아니라, 원본 해상도를 낭비하고 있을 때만 쓰는 회복 수단**이다.

| 상황 | imgsz 상향 | 판정 |
|---|---|---|
| 1920x1080 카메라 + imgsz 640 | 720/1080 의 정보를 버리는 중 | ✅ 효과 큼 |
| 720x404 + imgsz 640 | 약간 버리는 중 | ✅ 효과 있음 |
| 384x288 + imgsz 640 | 이미 전부 사용 중 | ❌ 효과 없음, 부작용 |

**결론: 진짜 제약은 카메라가 대상에게 몇 픽셀을 주느냐다.**
원본에 없는 정보는 소프트웨어로 만들어낼 수 없다.
저해상도 카메라에서 멀리 있는 사람이 작게 잡히면 **해결 수단이 없다** —
카메라 해상도를 올리거나, 더 가까이 설치하거나, 대수를 늘리는 수밖에 없다.

## 4-C. 내려다보는 각도 (CAVIAR 쇼핑센터 복도)

천장에서 내려다보는 실제 CCTV 영상으로 검증했다.
`ThreePastShop2cor.mpg` (384x288, 25fps, 1,521 frames, CC BY-SA, 리스본 쇼핑센터 2004년 녹화).

### 사람 크기 분포 — 한 화면에서 10배 차이

| | 화면 속 | 텐서 속(imgsz 640) |
|---|---|---|
| 최소 | 15px | 25px |
| 5% | 38px | 63px |
| 중앙값 | **64px** | **107px** |
| 95% | 128px | 214px |
| 최대 | 155px | 258px |

**최대/최소 = 10.2배** (store-aisle 은 4.7배).
관측의 **35%가 텐서 90px 기준 미달**, 7%가 65px 미달이다.

### 추적 품질 — 눈에 띄게 나빠졌다

| | store-aisle (65초) | CAVIAR (61초) |
|---|---|---|
| 고유 track | 7 | 11 |
| track당 최대 끊김 | 11회 | **49회** |
| **ID 뒤바뀜** | **0건** | **2건** |

지금까지 두 영상에서 0건이던 ID 뒤바뀜이 **처음으로 발생**했다.
복도 끝의 작은 사람들끼리 bbox 가 겹치는 지점이었다.

### ⚠ 이 비교는 각도만의 효과가 아니다

CAVIAR 는 store-aisle 과 **여러 조건이 동시에 다르다.**

| 조건 | store-aisle | CAVIAR |
|---|---|---|
| 각도 | 완만 | 가파름 |
| 해상도 | 720x404 | **384x288** |
| 사람 크기 중앙값 | **203px** | **64px** |
| 녹화 품질 | 최신 | 2004년, 압축 열화 |

따라서 **"내려다보는 각도 때문에 나빠졌다"고 말할 수 없다.**
측정 가능한 범위에서 지배적인 요인은 **사람의 픽셀 크기**(203px → 64px)이며,
각도 자체의 영향은 이 실험으로 분리되지 않는다.

→ 이 혼재를 풀기 위해 **거의 수직 시점 영상을 따로 구해 4-D 에서 재측정했다.**

## 4-D. 각도 효과를 분리하다 (거의 수직 시점)

4-C 의 혼재(각도와 사람 크기가 동시에 변함)를 풀기 위해,
**사람이 충분히 큰 수직 시점 영상**을 따로 구했다.

`topdown-plaza.mp4` (402x300, 30fps, 1,283 frames).
출처: `github.com/saimj7/People-Counting-in-Real-Time` 의 테스트 영상.
머리와 어깨 위주로 보이는 거의 수직 하향 시점이다.

### 크기 조건은 충족되었다

| | 값 |
|---|---|
| 사람 높이 중앙값 | **104px** |
| 텐서 속 환산 (imgsz 640 / 프레임 402) | **166px** |
| 우리 기준 | 90px 이상 |

**텐서 기준의 1.8배**로, 크기는 문제가 아닌 조건이다.
(참고: 2절 스케일 스윕에서 store-aisle 이 화면 속 102px / 텐서 90px 일 때 재현율 96% 였다.)

### 그런데 탐지 신뢰도가 떨어졌다

| 영상 | 화각 | 사람 높이 중앙값 | conf 중앙값 | conf 25% | **conf < 0.5 비율** |
|---|---|---|---|---|---|
| store-aisle | 완만 | 203px | 0.83 | 0.74 | **5%** |
| people-detection | 중간 | 194px | 0.87 | 0.80 | **4%** |
| CAVIAR 복도 | 가파름 | 64px | 0.77 | 0.54 | **21%** |
| **topdown-plaza** | **거의 수직** | **104px** | 0.80 | 0.61 | **16%** |

**topdown 은 CAVIAR 보다 사람이 1.6배 크고 텐서 기준으로는 2.6배인데도,
신뢰도 저하 정도가 CAVIAR 와 비슷하다.**

또한 같은 프레임에서 conf 를 0.25 → 0.05 로 낮추면 person 후보가
프레임당 1.53 → 2.20 개로 **44% 늘어난다.** 기본 임계값 아래에 깔린 사람이 있다는 뜻이다.

### 결론 — 각도는 크기와 별개의 독립 변수다

크기 조건을 충족해도 수직 시점에서는 탐지 신뢰도가 떨어진다.
COCO 로 사전학습된 detector 가 **위에서 내려다본 사람 이미지를 거의 보지 못했기 때문**으로 보인다.
사람을 위에서 보면 머리와 어깨만 남아 옆에서 본 사람의 형태와 전혀 다르다.

| 변수 | 영향 | 대응 |
|---|---|---|
| **사람 픽셀 크기** | 4-A~4-B 에서 측정 | 카메라 배치 / imgsz(원본 해상도까지) |
| **촬영 각도** | 크기와 독립. 수직일수록 신뢰도 하락 | **사전학습 모델로는 해결 불가** → 재학습 필요 |

즉 **천장 설치로 갈수록 "YOLO 재학습"이 선택이 아니라 필수에 가까워진다.**
원본 문서(§5)가 "직접 YOLO 재학습"을 뒤로 미룬 판단은 1차 구현에서는 옳았지만,
**최종 카메라가 천장 설치라면 이 항목의 우선순위가 올라간다.**

### 이 측정의 한계

- 영상마다 장면·조명·압축·해상도가 다르다. 각도만 바꾼 대조군이 아니다.
- 다만 **크기 혼재는 제거됐다** — topdown 은 크기 기준을 충분히 넘는데도 열화됐다.
- topdown 영상은 등장 인원이 1~2명이고 69% 프레임이 비어 있어 표본이 작다.
- 정답 라벨이 없어 "몇 명을 놓쳤는지"는 셀 수 없다. 신뢰도 분포로만 비교했다.

### 부수 발견 — 실제 CCTV 가 입력 계층 버그를 드러냈다

MPEG2 컨테이너가 `CAP_PROP_POS_MSEC` 로 비정상적으로 큰 값을 돌려주어
`timedelta` 계산이 `OverflowError` 로 파이프라인 전체를 중단시켰다.
지금까지 쓰던 mp4 에서는 나타나지 않던 문제다.

또한 이 파일은 메타데이터상 프레임 수가 **17** 로 보고되지만 실제로는 **1,521** 프레임이다.
**실제 녹화본의 메타데이터는 신뢰할 수 없다.**

수정: POS_MSEC 가 한 번이라도 비정상이면 이후 전부 fps 기반으로 전환한다.
회귀 테스트 `test_video_source_survives_broken_timestamps` 추가.

## 5. 이 측정이 말해주지 않는 것

- **ReID 고유의 한계를 분리하지 못했다.** 신원 유실이 시작된 지점(텐서 45px)에서는
  재현율이 이미 43%로 떨어져 있었다. 즉 **사람이 아예 탐지되지 않아서** track 이 끊긴 것인지,
  **임베딩이 약해져서** 재식별에 실패한 것인지 구분할 수 없다.
  `imgsz` 를 올려 탐지를 회복시키자 신원도 함께 회복된 것으로 보아,
  **적어도 텐서 45px 까지는 탐지가 병목이고 ReID 가 먼저 무너지지는 않는다.**
- **yolov8n 기준이다.** 더 큰 모델은 곡선 전체가 왼쪽으로 이동할 것이나 측정하지 않았다.
- **원근 왜곡은 재현하지 못한다.** 축소는 "멀어짐"을 흉내낼 뿐,
  천장에 높이 달았을 때 생기는 **내려다보는 각도**는 반영되지 않는다.
  머리 위에서 본 사람은 형태 자체가 달라 별도 검증이 필요하다.
- 한 영상 · 한 구간 기준이다.

## 6. 재현 명령

```bash
# 스케일 스윕
for s in 1.0 0.7 0.5 0.35 0.25 0.18 0.12; do
  python run_tracking.py --source data/videos/store-aisle-detection.mp4 \
    --scale $s --scale-mode shrink --start-frame 1200 --stride 2 --tracker-fps 30 \
    --max-frames 200 --no-video --out-dir outputs/sh-$s
done

# imgsz 축 검증
for z in 640 960 1280; do
  python run_tracking.py --source data/videos/store-aisle-detection.mp4 \
    --scale 0.25 --scale-mode shrink --imgsz $z --start-frame 1200 --stride 2 \
    --tracker-fps 30 --max-frames 200 --no-video --out-dir outputs/isz-$z
done
```

판정은 track 수가 아니라 **"구간 전체에 걸쳐 동일 ID 를 유지한 인원 수"** 로 한다.
track 수만 세면 붕괴를 놓친다(2절 참조).
