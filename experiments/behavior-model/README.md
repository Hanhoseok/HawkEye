# storeguard — 무인매장 행동 인식 시스템

IP 카메라(RTSP) 또는 MP4 영상에서 매장 내 사람 행동을 인식하고,
**이상행동이 보일 때만** 웹 대시보드에 실시간 알림을 띄우는 캡스톤디자인용 시스템이다.

현재 모델은 이상행동 3종과 정상 구매행동 6종을 **한 모델에서** 함께 분류하는
10클래스 통합 모델(`runs/unified_r2p1d`)이다.

| 그룹 | 클래스 | 알림 |
|---|---|---|
| 이상행동 (AI-Hub 238-2) | 전도, 파손, 절도 의심 | **알림 발생** |
| 구매행동 (AI-Hub 238-1) | 매장이동, 선택, 시험, 구매, 반품, 비교 | 알림 없음 (상태 표시만) |
| 라벨 구간 밖 | background_unlabeled | 알림 없음 |

구매행동을 함께 학습한 이유는 오경보다. 이상행동만 배운 모델은 상품을 집는 정상 동작을
파손·절도로 읽어 **정상 매장 영상에서 시간당 52.9건**의 오경보를 냈다.
정상 행동을 별도 클래스로 가르친 뒤, 같은 종류의 정상 영상 985개(21.3시간)에서
오경보가 **0건**이 되었다(4.4절. 측정 대상 집합이 달라진 점도 같이 적어 두었다).

결제 승인·거절, POS 연동, 위장 결제 판별은 이번 범위에 없다.
영상만으로 절도를 확정하지 않으며 **"절도 의심 행동"** 으로만 표시한다.

## 통합 모델 성능 (AI-Hub test 분할 — 영상 1,226개 / 25.3시간)

| 지표 | 값 |
|---|---|
| 클립 단위 정확도 / macro-F1 | 0.9799 / **0.9737** |
| 전도 사건 탐지율 | **100 %** (81/81), 지연 중앙값 1.67초 |
| 파손 사건 탐지율 | 98.8 % (80/81), 지연 중앙값 3.0초 |
| 절도 의심 사건 탐지율 | 90.2 % (74/82), 지연 중앙값 4.33초 |
| **정상 구매행동 영상의 시간당 오경보** | **0.00건** (985영상 / 21.3시간 / 오탐 0건) |
| 이상행동 영상의 시간당 오경보 | 7.46건 (241영상 / 4.0시간 / 오탐 30건) |
| 실시간 추론 지연 | 92.5 ms/클립 (GTX 1050 Ti) |

오경보를 두 줄로 나눠 적은 이유가 있다. 정상 매장에 가까운 조건에서는 0건이지만,
이상행동 영상 위에서는 기준 모델보다 **오히려 늘었다**(3.73 → 7.46건/시간).
행동 직전의 물색 동작에서 전도·절도 영상에 파손 알림이 붙는다. 자세한 내역은 4.3절에 있다.

**다른 출처의 매장 CCTV(Zenodo 794영상)에서는 쓸 수 있는 수준이 아니다.** 5절에 측정값이 있다.
같은 데이터셋 안에서 나온 위 수치를 실제 매장 성능으로 읽으면 안 된다.

## 2. 데이터에서 실제로 확인한 것

두 데이터셋을 쓴다. 성격이 달라서 따로 적는다.

| | 238-2 이상행동 | 238-1 구매행동 |
|---|---|---|
| 역할 | 알림 대상 행동 | **정상 행동(오경보 억제)** |
| 클래스 | fall, broken, theft | moving, select, test, buying, return, compare |
| 원본 fps (실측) | 3.0 | **매장이동 3.0 / 나머지 5종 10.0** |
| 해상도 (실측) | 1920×1080 | 1920×1080 |
| 영상 길이 | 60초 (180프레임) | 60초, 매장이동만 300초 |
| 캐시한 영상 수 | 2,169 | 5,009 (그중 3,181개를 이번에 추가 수집) |
| 분할 방식 | **배포 분할 그대로** (test = 배포 Validation) | 배포본이 일부만 내려와 있어 **take 단위로 직접 분할** |

캐시된 영상 합계 **7,178개**. 분할에 들어간 것은 7,173개다
(5개는 아래 "공식 배포 분할의 누수" 때문에 제외).

> **fps 가 데이터셋 안에서도 다르다.** 모델은 3 fps 로 통일해 쓰는데 원본은 아래처럼 섞여 있다.
> 라벨 프레임은 **원본 fps 좌표**이므로 캐시 좌표로 환산해야 한다.
>
> | 클래스 | 원본 fps | 라벨 프레임 | 캐시 프레임 | 변환 배율 |
> |---|---|---|---|---|
> | 전도·파손·절도 | 3 | 180~181 | 180~181 | 1.00 |
> | 매장이동 | 3 | 901~902 | 901~902 | 1.00 |
> | 선택·시험·구매·반품·비교 | 10 | 600~601 | 180~181 | **0.30** |
>
> 이 환산을 빼먹으면 구매행동 5종의 라벨이 전부 **약 3.3배 뒤로** 밀린다. 그래서 fps 를
> 상수로 박지 않고 `clips.label_scale()` 이 **캐시 길이 ÷ 라벨 길이**로 매 영상마다 계산한다.
> 같은 데이터셋 안에서도 배율이 1.00 과 0.30 으로 갈리므로 이 방식이어야 맞는다.
> selftest 항목과 몬타주 이미지로 확인했다.

### XML 구조에서 주의할 점

`meta/task/labels` 에는 fire/smoke/abandon/fight/weak pedestrian 까지 **8종이 항상 선언**되어 있다.
이것은 CVAT 프로젝트 스키마일 뿐이며 실제 라벨이 아니다. **실제 라벨은 `<track>` 요소에만 있다.**
이 구분을 놓치면 존재하지 않는 클래스를 학습시키게 된다.

### 공식 배포 분할의 누수

같은 촬영 사건(동일 시각·시나리오·배우)이 카메라별로 Training 과 Validation 에 갈라져 있는 경우가
**3건** 있다. 예: `C_3_7_48_BU_DYB_10-17_10-23-53_CA` (Training) 와 `..._CB/CC/CD/CE` (Validation).
그대로 쓰면 학습 데이터가 시험 데이터에 새어 든다. `storeguard.data.split` 이 이 take 의
Training 쪽 영상 5개를 자동으로 제외한다.

### `background_unlabeled` 는 "정상"이 아니다

이상행동 영상의 이벤트 구간 밖에서 뽑은 클립이다. 행동 직전의 접근·물색 동작이 섞여 있으므로
**"정상(normal)"이라고 부르지 않는다.** 진짜 정상 행동은 238-1 의 6개 클래스가 담당한다.
이 구분 덕분에 "정상 매장 영상의 오경보"를 실제로 측정할 수 있게 되었다(4.4절).

### 분할 누수 방지 규칙

1. `take`(같은 매장·시각·시나리오로 여러 카메라가 찍은 한 번의 연기) 단위로 **먼저** 자른다.
2. 클립은 분할 **뒤에** 만든다.
3. 238-2 는 배포 분할을 존중하고(`split.honor_deployed_test_datasets`), 238-1 은 직접 나눈다.
   238-1 배포본이 일부만 내려와 있어 일부 클래스가 Validation 쪽에만 존재하기 때문이다.
   그대로 쓰면 해당 클래스의 학습 데이터가 0이 된다.
4. `data/index/splits.json` 의 `누수검사` 항목에 교집합 검사 결과가 들어 있다(전부 빈 목록).

## 3. 설치와 실행 (Windows PowerShell)

### 3.0 이 PC에서는 지금 바로 됨

데이터 수집·캐시·학습이 모두 끝나 있고 `.env` 도 만들어져 있다. 아래 한 줄이면 대시보드가 뜬다.

```bash
cd D:\computervision; .\scripts\run_dashboard.cmd --loop
```

브라우저에서 `http://127.0.0.1:8000` 을 연다. 종료는 `Ctrl+C`.
런처는 `runs\unified_r2p1d\best.pt` 가 있으면 통합 모델로, 없으면 `baseline_r2p1d` 로 뜬다.

`--loop` 는 데모용으로 입력 영상을 끝나면 처음부터 다시 재생한다. 기본 입력은 `.env` 의
`CAM1_SOURCE` 이며 지금은 전도 시험 영상이 들어 있어 약 45초 지점에서 알림이 뜬다.

**영상을 바꾸려고 `.env` 를 고칠 필요는 없다.** 대시보드의 카메라 카드에 있는
`◀ 이전` / `다음 ▶` 버튼으로 시험 분할 영상을 넘겨 볼 수 있고,
옆의 드롭다운으로 클래스를 골라 볼 수도 있다.
재생목록에는 mp4 가 디스크에 남아 있는 **562개 영상(9클래스)** 이 들어가며,
같은 클래스가 줄줄이 나오지 않도록 섞여 있다.
같은 카드의 입력칸에 RTSP 주소를 넣고 `RTSP 연결` 을 누르면 실제 IP 카메라로 바로 전환된다.

구매행동 영상(매장이동·선택·시험·구매·반품·비교)에서는 **알림이 뜨지 않고 상태 표시만 바뀌는 것**이
정상 동작이다. test 분할의 구매행동 영상 985개(21.3시간)에서 오탐이 0건이었다(4.3절).
통합 모델이 하는 일이 그것이다.

> **`.ps1` 이 "이 시스템에서 스크립트를 실행할 수 없으므로" 오류로 막히는 경우**
> Windows 의 PowerShell 실행 정책 기본값이 `Restricted` 라서 `.ps1` 파일 실행이 차단된 것이다.

### 4.1 모델 선정 근거

| 후보 | 판단 |
|---|---|
| 단일 프레임 객체 검출 + 규칙 | **탈락.** 넘어짐/앉음, 물건 집기/훔치기를 한 프레임으로 구분할 수 없다 |
| 포즈(키포인트) 기반 | **보조로만.** 파손·절도는 손·상품·집기의 관계가 핵심인데 골격만으로는 사라진다. 게다가 이 데이터는 전 프레임 키포인트가 없다(중앙값 63/180) |
| 사람 검출·추적 + 사람 크롭 분류 | **다음 단계.** 작은 인물 문제를 풀지만 검출기·추적기가 VRAM 4 GB 예산과 지연을 잡아먹고, 이 데이터에는 학습용 사람 박스가 없다 |
| **전체 프레임 RGB 클립 분류 (채택)** | 시간 문맥 + 장면 문맥을 함께 본다. 학습/추론 경로가 같아 실시간 조건을 정확히 맞출 수 있다 |

백본은 **`r2plus1d_18` (Kinetics-400 사전학습, torchvision)** 을 썼다.
(2+1)D 분해로 같은 연산량에서 순수 3D 보다 정확하고, 학습 해상도 112 가 4 GB VRAM 에 맞는다.
처음부터 학습하지 않고 **전이학습**한다.

같은 GPU에서 후보 백본을 실측 비교한 결과다 (배치 8 학습 / 배치 1 추론, cudnn 워밍업 후).

| arch | 학습 처리량 | 추론 지연 | 판단 |
|---|---|---|---|
| r2plus1d_18 | 4.4 clips/s | 75.2 ms | **채택.** 속도 차이가 작고 (2+1)D 가 정확도에 유리 |
| mc3_18 | 5.4 clips/s | 61.2 ms | 더 가볍다. VRAM 이 부족하면 이쪽 |
| r3d_18 | 5.7 clips/s | 58.3 ms | 가장 빠르지만 같은 계열에서 정확도가 낮다고 알려져 있다 |

추론 지연 차이(75 vs 58 ms)는 초당 1회 추론이라는 사용 조건에서 의미가 없었다.
그래서 속도가 아니라 정확도 쪽을 택했다.

|---|---|---|---|---|

- **알림 종류별**: 파손 25건, 절도 5건, 전도 0건.
- **발생한 영상별**: 전도 영상 16건, 절도 영상 14건, **파손 영상 0건, 구매행동 영상 0건.**

즉 오경보는 정상 손님이 아니라 **다른 이상행동 영상 안에서** 난다.
파손 precision 이 0.923 으로 가장 낮은 것과 같은 원인이고,
운영 관점에서는 "이상행동인 건 맞는데 종류가 틀린" 알림이다.

**매장별 편차** (알림 대상 사건이 있는 매장만)

| 매장 | 영상 | 알림대상 정답 사건 | 사건 탐지율 | 시간당 오경보 |
|---|---|---|---|---|
| DYB (대형유인매장B) | 376 | 116 | 0.957 | 1.14 |
| SMC (소형무인카페C) | 137 | 112 | 0.982 | 7.44 |
| DYA (대형유인매장A) | 209 | 16 | **0.875** | 0.59 |

SMA/SMB/SYA/SYB 는 구매행동 영상만 있어 탐지율이 정의되지 않는다. 네 매장 모두 **오탐 0건**이다.
DYA 는 알림 대상 사건이 16건뿐이라 수치가 흔들린다. 그래도 같은 모델이 매장에 따라
탐지율 0.88~0.98 사이에서 움직인다는 사실은 분명하다. **일곱 매장 모두 학습에도 등장한다.**
완전히 새로운 매장의 성능은 이보다 낮다고 보는 것이 안전하다(5절이 그 증거다).

### 4.4 기준 모델과의 비교 — 통합 모델이 실제로 바꾼 것

`baseline_r2p1d` 는 이상행동 3종 + background 만 배운 4클래스 모델이다.
두 모델을 같은 평가 도구로 돌린 결과를 나란히 둔다.

| 항목 | baseline (4클래스) | unified (10클래스) |
|---|---|---|
| **정상 구매행동 영상의 시간당 오경보** | **52.9** | **0.00** |
| ↳ 측정 대상 | 133영상 / 3.42시간 / 오탐 181건 | 985영상 / 21.28시간 / **오탐 0건** |
| 오경보가 난 정상 영상 비율 | 104 / 133 (78 %) | **0 / 985 (0 %)** |
| 이상행동 사건 탐지 (동일 241영상) | 234 / 244 (0.959) | 235 / 244 (**0.963**) |
| 이상행동 영상의 시간당 오경보 (동일 241영상) | 3.73 | 7.46 |
| 클립 단위 macro-F1 | 0.9570 (4클래스 기준) | 0.9737 (10클래스 기준) |

읽는 법을 분명히 해 둔다.

- **정상 영상 측정 대상이 서로 다르다.** baseline 의 52.9 는 구매행동 데이터를 일부만
  내려받았을 때의 test 분할(133영상)에서 쟀고, unified 의 0.00 은 데이터를 전량 수집한 뒤의
  test 분할(985영상)에서 쟀다. 두 집합이 같지 않으므로 **"52.9 → 0.00" 을 같은 영상에 대한
  전후 비교로 읽지 말 것.** 다만 unified 는 985영상 전체에서 오탐이 0건이므로, 어떤 부분집합을
  골라도 unified 쪽은 0이다. 같은 집합에서 baseline 을 다시 재는 측정은 진행 중이다.
- **정상 매장 조건의 오경보가 없어졌다.** baseline 은 구매 22/22, 시험 30/31, 반품 17/19 에서
  오경보를 냈다. 상품에 손을 뻗는 동작을 한 번도 "정상"으로 본 적이 없었기 때문이다.
  unified 는 985개 정상 영상 전체(21.3시간)에서 알림을 한 건도 내지 않았다.
- **이상행동 탐지력은 유지됐다.** 같은 241영상에서 234→235건. 클래스를 6개 늘려도 떨어지지 않았다.
- **이상행동 영상 안의 오탐은 늘었다(15 → 30건).** 파손 알림 25건 + 절도 알림 5건이고,
  전도·절도 영상에서 난다. 정상 손님에게 가는 오경보가 아니므로 운영상 비용은 낮지만,
  **개선이 아니라 악화다.**
  파손 임계값을 올리면 줄겠지만 그 조정은 val 분할에서만 해야 하므로 지금은 손대지 않았다.
- 두 모델의 macro-F1 은 클래스 수가 달라 **직접 비교할 수 없다.**

같은 측정을 다시 하려면:

```bash
cd D:\computervision; .\.venv\Scripts\python.exe -m storeguard.tools.false_alarm --run unified_r2p1d --compare baseline_r2p1d --split test
```

### 4.7 사건 단위 평가의 매칭 규칙

- 알림(클래스 c, 시각 t)이 같은 클래스 정답 사건의 `[start − 3초, end + 3초]` 안에 들면 매칭.
- **정답 사건 1개당 가장 빠른 알림 1건만 TP.** 이후 매칭되는 알림은 '중복 알림'으로 따로 센다.
  중복을 여러 번 정답으로 세지 않는다.
- 어떤 정답 사건에도 안 붙는 알림은 오탐(FP). 구매행동 영상의 알림은 전부 FP 가 된다.
- 탐지율 분모는 **알림 대상 클래스(전도/파손/절도)의 정답 사건만** 센다.
  구매행동 사건을 분모에 넣으면 탐지율이 가짜로 떨어진다.
- 탐지 지연 = 알림 시각 − 사건 시작 시각.
- 오프라인 평가와 실시간 추론이 **같은 `AlertEngine` 코드**를 쓴다. 평가용 별도 규칙이 없다.

| 증상 | 원인 | 조치 |

| 구매행동 라벨이 약 3.3배 뒤로 밀릴 수 있었음 | 라벨은 원본 fps 좌표. 같은 데이터셋 안에서도 원본이 10 fps(5종)와 3 fps(매장이동)로 섞여 있다 | fps 상수 대신 `label_scale()` = 캐시 길이 ÷ 라벨 길이로 영상마다 계산. selftest + 몬타주 이미지로 검증 |
| 매장이동 클립이 다른 클래스의 33배 | 300초 영상에서 사건 하나가 영상 전체 → 클립이 영상당 74개 | 사건별 균등 추출 + `max_pos_per_video` 상한 |

| 매장별 탐지율이 0.04 로 표시 | 구매행동 사건(알림 안 하는 클래스)이 탐지율 분모에 들어갔다 | 분모를 알림 대상 사건으로 한정, 리포트 생성기도 구버전 JSON 을 재집계 |

## 5. 다른 출처 영상에서의 일반화 — 측정 결과 "안 된다"

AI-Hub 데이터로 낸 4절 수치는 **같은 데이터셋 안에서의 성능**이다.
실제 매장에서 쓸 수 있는지 보려면 다른 출처의 영상이 필요하다.
공개 매장 절도 데이터셋(Zenodo)으로 측정했다.

```bash
cd D:\computervision; .\.venv\Scripts\python.exe -m storeguard.tools.eval_external --run unified_r2p1d --normal "<normal 폴더>" --positive "<shoplifting 폴더>" --positive-class theft --sampling both
```

### 5.1 이 데이터가 학습 데이터와 다른 점

| 항목 | 학습 데이터 (AI-Hub) | 외부 데이터 (Zenodo) |
|---|---|---|
| 영상 수 | — | normal 363 / shoplifting 431 |
| 해상도 | 1920×1080 | **640×352** |
| fps | 3 또는 10 | 30 |
| 영상 길이 | 60초 / 300초 | 중앙값 **3.9초** (최소 2.5초) |
| 모델 입력 1개(5.33초)보다 짧은 영상 | 0 % | **99.9 %** |
| 행동 | 연출 | 실제 매장 CCTV |

영상이 모델 입력 길이보다 짧아서 샘플링 방식을 두 가지로 재서 함께 보고한다.
`uniform` 은 영상 전체에서 16프레임을 균등 추출, `fps_pad` 는 3 fps 로 뽑고 모자란 만큼 패딩한다.

### 5.2 결과

운영 임계값(전도 0.55 / 파손 0.60 / 절도 0.65)에서 영상 단위로 집계했다.

| 지표 | baseline (4클래스) | unified (10클래스) |
|---|---|---|
| 정상 영상에 알림이 뜬 비율 — uniform | 16.3 % (59/363) | **3.3 %** (12/363) |
| 정상 영상에 알림이 뜬 비율 — fps_pad | 10.2 % (37/363) | **1.1 %** (4/363) |
| 절도 영상 탐지율 — uniform | 19.3 % | **3.5 %** |
| 절도 영상 탐지율 — fps_pad | 17.6 % | **1.4 %** |
| 절도 점수 AUC (정상 대비) — uniform | 0.587 | **0.671** |
| 절도 점수 AUC (정상 대비) — fps_pad | 0.589 | 0.652 |

통합 모델은 **훨씬 조용해졌지만 그만큼 못 잡는다.** 오탐이 5분의 1로 줄었는데
절도 탐지율도 5분의 1 이하로 줄었다. AUC 가 0.59 → 0.67 로 올랐으니 점수의 순서 자체는
조금 나아졌지만, 0.67 은 쓸 수 있는 값이 아니다(0.5 가 무작위).

임계값을 낮춰 보면 교환 관계가 분명히 보인다(통합 모델, uniform).

| 임계값 | 정상 오탐률 | 절도 탐지율 |
|---|---|---|
| 0.05 | 29.2 % | 55.7 % |
| 0.10 | 16.5 % | 32.7 % |
| 0.30 | 5.5 % | 13.2 % |
| 0.65 (운영값) | 1.4 % | 3.5 % |

`탐지율 − 오탐률` 이 가장 큰 지점이 임계값 0.05 인데, 거기서도 정상 영상 10개 중 3개에 알림이 뜬다.
**이 데이터에는 쓸 만한 동작점이 없다.**

### 5.3 왜 안 되는가, 그리고 무엇이 필요한가

원인은 세 가지로 갈린다. 어느 쪽이 지배적인지는 아직 분리하지 못했다.

1. **입력 길이 불일치.** 영상의 99.9 %가 모델 입력 1개보다 짧다. 모델은 5.33초의 시간 문맥으로
   판단하도록 배웠는데 3.9초짜리를 늘리거나 패딩해서 넣고 있다.
2. **촬영 조건 차이.** 640×352 / 30 fps / 실제 매장 조명·각도. 학습 데이터는 1080p 연출 영상이다.
3. **행동 양식 차이.** 연출된 절도와 실제 절도의 동작이 다르다.

정직한 결론은 이렇다. **이 모델을 새 매장에 그대로 붙이면 안 된다.**
쓰려면 다음이 필요하다.

1. 설치 매장에서 **그 매장 영상**을 모아 추가 학습(fine-tuning)한다.
2. 추가 학습 전/후 성능을 따로 기록한다(같은 수치로 뭉뚱그리지 않는다).
3. 그 매장의 정상 영업 영상으로 임계값을 **val 분할에서** 다시 잡는다.

원자료: [runs/unified_r2p1d/eval_external.json](runs/unified_r2p1d/eval_external.json)
(영상별 점수, 임계값 스윕, 운영곡선 포함)

| 실제 상점 운영 환경에서의 성능 | **미측정** | 설치 매장 영상이 없다. 5절의 결론대로 추가 학습이 선행되어야 한다 |
| 새 매장 추가 학습 전/후 비교 | **미수행** | 직접 촬영한 소형 매장 영상이 아직 없다 |
| `split.mode: store` 매장 분리 평가 | **미수행** | 코드는 있으나 실행하지 않았다. 새 매장 일반화의 하락 폭을 보려면 이것부터 돌려야 한다 |
| 파손 임계값 재조정 | **미수행** | 이상행동 영상 내 오탐 25건의 주원인. val 분할에서만 조정해야 한다 |
| 실제 RTSP IP 카메라 연결 | **미수행** | 이 PC에 접근 가능한 IP 카메라가 없다. 코드 경로는 구현·검토되었으나 실제 카메라로 확인하지 않았다 |
| 배우 분리 평가 | **불가** | 배우 코드가 개인 식별자가 아니다 |
| 사람별 중복 알림 억제 | **구현 안 함** | 추적 ID가 없다. 억제 단위는 카메라 × 클래스다 |
| 사람 바운딩박스 표시 | **구현 안 함** | 전체 클립 분류 모델이라 특정 사람에게 행동을 귀속할 근거가 없다 |
| 모델 점수 보정(calibration) | **미수행** | 현재 점수는 확률이 아니다. UI/문서에 그렇게 명시했다 |
| 다중 카메라 동시 운용 장시간 부하 | **부분 측정** | 3대 동시 구동 지연은 쟀다(3.0절). 장시간 안정성은 안 쟀다 |

### 다른 매장에서도 같은 성능이 나온다고 가정하지 않는다

이 데이터의 7개 매장은 모두 같은 촬영팀이 같은 시나리오로 연출한 것이다.
조명, 매대 배치, 카메라 각도, 배우 행동 양식이 실제 매장과 다르다.

측정된 근거가 두 개 있다.

1. 같은 데이터셋 안에서도 **매장별 사건 탐지율이 0.875~0.982 로 갈린다**(4.3절).
   그것도 일곱 매장 모두 학습 데이터에 포함된 상태에서다.
2. 다른 출처 영상에서는 **운영 임계값 기준 절도 탐지율이 3.5 %** 다(5절).

## 7. 배포 시 주의 (외부망 접근)

매장 카메라에 외부에서 접근해야 할 때 **RTSP 포트(554)를 인터넷에 직접 열지 않는다.**
RTSP 는 기본 인증이 약하고 스캐너에 바로 노출된다. 다음 중 하나를 쓴다.

1. **VPN** (WireGuard / OpenVPN) — 매장 공유기에 VPN 서버를 두고 분석 PC가 VPN 으로 붙는다. 권장.
2. **제조사 P2P/클라우드 릴레이** — 간편하지만 제조사 서버를 거치므로 영상이 외부로 나간다.
3. **역방향 터널** (예: Tailscale, Cloudflare Tunnel) — 포트 개방 없이 연결.

어느 쪽이든 카메라 계정은 전용 계정을 만들고, 이 시스템에는 **읽기 전용 권한**만 준다.
`.env` 는 공유·커밋하지 않는다(`.gitignore` 에 들어 있다).
