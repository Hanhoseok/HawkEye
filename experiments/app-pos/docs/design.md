# 관리자 앱 · 경보 서버 · 영상 중계 설계

담당: 한호석 · 작성: 2026-10-01

파이프라인이 낸 경보를 관리자 폰으로 전달하고, 관리자가 처리한 결과를 기록한다.
매장 카메라 영상은 RTSP로 중계해 앱에서 실시간으로 본다.

## 1. 범위

| 포함 (한호석) | 포함하지 않음 (다른 팀원) |
|---|---|
| 경보 서버 (`server/`) | 사람·물건 탐지, 추적 (왕규원) |
| 안드로이드 관리자 앱 (`app/`) | 모의 결제 시스템, 결제 개수 대조 (왕규원) |
| RTSP 중계기 설정 (`relay/`) | 행동 인식 모델 (정준우) |
| 경보 전송 클라이언트·시뮬레이터 (`client/`) | |

## 2. 결정 사항

> **탐지 방식과 분리한다 (2026-10-01).** 팀의 최종 탐지 방식(정준우 모델 / 왕규원 파이프라인 / 혼합)이 아직 정해지지 않아,
> 다른 팀원 폴더는 수정하지 않는다. 경보 전송은 이 폴더의 독립 클라이언트(`client/`, 표준 라이브러리만 사용)로 두고,
> 방식이 정해지면 `final/` 통합 때 붙인다. 앱·서버가 아는 것은 §5의 경보 JSON 형식 하나뿐이다.

| 항목 | 결정 | 이유 |
|---|---|---|
| 시연 | 녹화 영상으로 끝까지 연결 → 이후 실시간 카메라로 교체 | 녹화/실시간을 같은 구조로 교체 가능하게 설계 |
| 앱 | Kotlin + Jetpack Compose (안드로이드) | RTSP 기본 재생(Media3), 개발 PC에서 빌드·에뮬레이터 검증 가능 |
| 서버 | Python 3.11 + FastAPI + SQLite | 파이프라인과 같은 언어, 파일 하나로 저장 |
| 알림 | 앱이 서버와 WebSocket 연결 유지 (포그라운드 서비스) | Firebase 계정 불필요 |
| 영상 | MediaMTX 중계기 → 파이프라인·앱에 분배 | 카메라 동시 접속 제한 회피, 카메라 계정을 앱에 넣지 않음 |
| 장면 사진 | 파이프라인이 경보 순간 프레임을 JPEG로 첨부 | 녹화·실시간 모두 같은 방식. 클립은 2차 |
| 배포 위치 | 개발은 노트북, 서버는 나중에 AWS로 옮길 수 있게 | 앱은 서버 주소를 설정에서 바꾼다 |

## 3. 구성

```
[카메라 옆 PC]
 카메라 ─RTSP─▶ MediaMTX ─┬─▶ 파이프라인 ──경보 POST(JSON+사진)──▶ 경보 서버 ──WebSocket──▶ 앱
 (녹화 단계: 영상 파일)    │                                      (FastAPI+SQLite)
                           └──────────────── RTSP (라이브 화면) ───────────────────────▶ 앱
```

## 4. 사건(case) 규칙

파이프라인은 한 손님에 대해 경보를 여러 번 낸다 (출구 접근 `WARNING` → 퇴장 `HIGH_RISK`, 또는 `REVIEW`/`CLEAR`).
서버는 **(실행 번호 `run_id`, 카메라 `camera_id`, 손님 번호 `person_id`) 하나를 사건 하나**로 묶는다.
`run_id`가 필요한 이유: 파이프라인을 다시 켜면 손님 번호가 1부터 다시 시작한다.

| 단계 | 순위 | 뜻 |
|---|---|---|
| `CLEAR` | 0 | 집은 것 없음 또는 그만큼 결제 |
| `WARNING` | 1 | 미결제로 출구에 다가섬 (아직 안 나감) |
| `REVIEW` | 2 | 일부만 결제 또는 신원 뒤바뀜 의심 — 관리자 확인 필요 |
| `HIGH_RISK` | 3 | 미결제로 나감 (확정) |

사건 상태(`state`):

| 상태 | 언제 |
|---|---|
| `active` | 경보 단계(WARNING/REVIEW/HIGH_RISK)이고 관리자가 아직 처리하지 않음 |
| `auto_cleared` | WARNING이었다가 CLEAR가 옴 (결제했거나 되돌아옴) |
| `pass` | 처음부터 CLEAR (경보 없이 통과, 오경보 통계용) |
| `resolved` | 관리자가 처리함 |

새 경보가 들어올 때:

1. 사건이 없으면 만든다. 경보 단계면 `active` + **알림**, CLEAR면 `pass` (알림 없음).
2. 사건이 있고 순위가 **올라가면** 단계를 올리고 `active` + **알림**. 관리자가 처리했던 사건이어도 다시 연다(처리 기록은 이력에 남는다).
3. WARNING 상태에서 CLEAR가 오면 `auto_cleared` (조용히 갱신, 폰 알림 지움).
4. 같은 순위거나 내려가면 숫자·사진만 갱신 (알림 없음). 이미 확정된 단계(REVIEW/HIGH_RISK)는 CLEAR로 내리지 않는다.

관리자 처리: `paid_confirmed`(결제 확인 완료) / `false_alarm`(잘못된 알림). 처리 이력은 모두 남긴다.

## 5. API

인증: 환경변수 `HAWKEYE_API_KEY`가 설정되면 모든 요청에 헤더 `X-API-Key` 필요 (WebSocket은 `?key=`). 비어 있으면 인증 없음(로컬 개발).

| 메서드 | 경로 | 용도 |
|---|---|---|
| `POST` | `/api/events` | 탐지 쪽 → 경보 하나 (아래 형식) |
| `GET` | `/api/cases` | 사건 목록. `state`, `updated_since`(ISO8601), `limit` |
| `GET` | `/api/cases/{id}` | 사건 상세 + 경보 이력 + 처리 이력 |
| `POST` | `/api/cases/{id}/resolution` | `{"resolution": "paid_confirmed" \| "false_alarm", "note": "..."}` |
| `GET` | `/api/events/{id}/snapshot.jpg` | 장면 사진 |
| `GET` | `/api/stats` | 상태·처리별 개수 (오경보율 계산용) |
| `GET` | `/api/config` | 앱 설정 (라이브 RTSP 주소 목록) |
| `GET` | `/healthz` | 상태 확인 |
| `WS` | `/ws` | 서버 → 앱 실시간 메시지 |

### 경보 입력 (`POST /api/events`)

파이프라인 `RiskEvent.to_dict()`에 세 필드를 더한다.

```json
{
  "run_id": "2026-10-01T15:20:11-a1b2",
  "camera_id": "cam1",
  "event": {
    "person_id": 3, "level": "WARNING", "zone": "EXIT", "frame": 1043,
    "timestamp": "00:00:34.766", "time_sec": 34.766, "bbox": [610, 280, 780, 700],
    "taken": 2, "paid": 1, "unpaid": 1, "take_frames": [[812, 840]],
    "reason": "...", "identity_check": 0.82,
    "items": [{"name": "과자", "taken": 2, "paid": 1}]
  },
  "snapshot_jpeg_b64": "<선택: base64 JPEG>"
}
```

`items`는 선택 항목이다. 왕규원 선반 지도 3단계(품목별 개수)가 들어오면 채워지고, 앱은 있을 때만 품목별로 보여준다.

### 실시간 메시지 (`WS /ws`)

```json
{"type": "case.updated", "notify": true, "case": { ...사건 요약... }}
```

`notify`가 `true`일 때만 앱이 폰 알림을 띄운다. 연결이 끊겼다 붙으면 앱은 `GET /api/cases?updated_since=<마지막 수신 시각>`으로 놓친 사건을 받는다.

## 6. 오류 처리

| 상황 | 처리 |
|---|---|
| 서버가 꺼져 있음 | 전송 클라이언트는 별도 스레드에서 재시도하고, 호출한 쪽(영상 처리)은 멈추지 않는다 |
| 전송 대기열이 가득 참 | 가장 오래된 것을 버리고 경고 로그 |
| 잘못된 경보 형식 | 422 응답, 저장하지 않음 |
| 앱 연결 끊김 | 지수 백오프로 재연결, 재연결 후 놓친 사건 조회 |
| 사진 없음 | 사건은 저장하고 사진만 비움 |

## 7. 시험

- 서버: 사건 규칙(순수 함수), API, WebSocket 알림을 pytest로 시험
- 전송 클라이언트: 재시도·대기열·비차단·실제 HTTP 시험, 시뮬레이터 시나리오를 실제 서버 코드에 통과시켜 사건 상태 확인
- 앱: 서버 응답 파싱·상태 갱신 단위 시험 + 에뮬레이터에서 화면 확인
- 연결 시험: 시뮬레이터 → 서버 → 에뮬레이터 앱 알림 (실제 파이프라인 연결은 `final/` 통합 때)
